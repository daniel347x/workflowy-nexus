## 0. Context and baseline (already shipped — do not re-do)

The 2026-08-20 incident: an agent loop-fired `beacon.map.refresh` across 4–5 files; ~dozens of detached CARTO workers ran concurrently at an experimental 0.25s write delay (~12 writes/s aggregate); Workflowy locked the account's writes (`403 WFB(3)`); zombie workers kept hammering for ~an hour through a silent legacy fallback with no logging, no kill path, and no visibility.

Already shipped (commits `31ab3dc`, `5613e4f`):

- `APIResponseError` fail-fast on ordinary 4xx (status + ≤1000-char body retained; 401/404/429 keep specialized types; 5xx stays retryable `NetworkError`).
- Permanent API errors and cancellation no longer enter the legacy fallback.
- Cooperative cancellation: workers poll the CARTO job JSON; all core CRUD retry/rate-limit sleeps poll cancellation every 250 ms (`_sleep_with_operation_cancel`).
- Exact-key (`root_uuid`+`mode`) launch dedupe, file-backed and cross-process (scans the shared jobs dir). This is an un-mutexed file scan — v5 replaces it with the mutexed admission transaction.
- `API_RATE_LIMIT_DELAY` restored to 1.0s (`api_client_core.py:41`), with an in-code comment forbidding lowering it without a cross-process governor.
- 429 retries are bounded (`max_retries`, backoff, cancel-aware sleeps) and raise on exhaustion.
- Regression tests: 403 fail-fast, cancel-during-backoff, duplicate-job admission.

This spec is the guardrail layer on top of that substrate.

## 1. Design principles (inviolable)

1. **Deny by default.** Anything unclassifiable is treated as active/running and is never reaped, killed, or bypassed. An undiscovered edge case degrades to a refusal or a visibly-stuck job in the widget — never to an account lockout.
2. **Fail loud, never silently degrade.** No hidden fallback paths anywhere in the write pipeline.
3. **Never reap or kill on indeterminate PID state.** `unknown` liveness ≡ alive.
4. **Every refusal is a teaching error** — it names the conflicting job/path, the reason, and what to do next.
5. **One shared launch authority.** Every CARTO_REFRESH worker is launched by the same function, from every call site.
6. **Heartbeat is diagnostic-only.** It never authorizes a reap or a kill; PID identity is the only death authority.
7. **Reads are ungoverned.** WFB(3) blocked writes only; reads kept working during the incident. Cache-refresh coordination (`.refresh_claims`) already exists separately and is untouched. (Read *pacing* — the existing per-iteration `API_RATE_LIMIT_DELAY` sleeps on the read sites — is kept; see §5.1.)
8. **Sentinel = cancellation authority; claim release or PID death = stop authority; job status = presentation only.** These three roles are never conflated.
9. **One exit door.** Every admitted job — success, failure, cancellation, spawn failure, or **a claim whose owner PID died** (reaped) — ends through the same atomic finalize primitive.

## 2. Architecture overview — four concerns

| Concern | Mechanism | Module |
|---|---|---|
| **Global write pacing** | Account-scoped ticketed write governor + WFB(3) circuit breaker, enforced at the six write sites through one send authority | `carto_write_governor.py` (new, dependency-light) |
| **Region ownership** | Machine-wide path + Workflowy-graph footprint claims with overlap detection, cooldown tombstones, semantic dedupe | `carto_job_governance.py` (new) |
| **Worker lifecycle control** | Cancellation sentinels, `cancelling` presentation state, PID-identity liveness, exact-PID force kill, atomic `finalize_claim`, startup sweep, prepared-launch handoff (F12+4/F12+5 + F12-on-AST) | `carto_job_governance.py` + edits to `server.py`, `weave_worker.py`, `markdown_generate_pipeline.py` |
| **Observability** | mtime heartbeat files + job JSON progress (existing) surfaced to the widget; `cancelling` presentation overlay in the scanner | `weave_worker.py`, `_scan_carto_job_files`, extension client (Phase F) |

Two OS mutexes serialize the two cross-process transaction types (separate because hold-time profiles and scoping differ):

- **admission.mutex** — *machine-wide* (per runtime dir), held per job launch/finalize/GC transaction.
- **write_slot.mutex** — *account-scoped*, held per write-ticket issuance and every breaker transition.

Both are OS-level locks (`msvcrt.locking` with a retry loop on Windows — `LK_LOCK` has a ~10 s built-in cap; `fcntl.flock` on POSIX) and are therefore released by the OS if the holder crashes. On any async path, lock acquisition uses **non-blocking attempts** (`LK_NBLCK` / `LOCK_NB`) with short cancel-aware `asyncio` sleeps between attempts — a blocking `LK_LOCK` call on the MCP event-loop thread would wedge every WS handler for up to ~10 s. Synchronous detached-worker paths may use a synchronous polling wrapper. **The two mutexes are NEVER held simultaneously:** no code path acquires `write_slot.mutex` while holding `admission.mutex`, or vice versa. Region metadata transactions finish and release before any governed Workflowy write or breaker transition begins.

**Mutex holds are milliseconds-scale, always.** No source-file mutation, no Workflowy mutation, no governed API wait, no snapshot rewrite, no subprocess spawn-wait, and no arbitrary user-supplied callback executes while `admission.mutex` or `write_slot.mutex` is held. **Small governance/job metadata writes that constitute the transaction itself are permitted and required** — creating a claim file, creating the initial job JSON, writing a tombstone, updating governor/breaker JSON, and the §8 claim-adoption writes all happen under their mutex by design. The prepared-launch callbacks (F12+4/F12+5 and F12-on-AST) are the motivating unbounded-work cases and run *under a claim but outside the mutex* (§8).

## 3. State layout — machine-wide vs account-scoped

All governance state lives under the CARTO jobs root returned by the ONE authoritative helper `get_cartographer_jobs_dir()` (the byte-identical value exposed by `_get_carto_jobs_base_dir()`). Resolution: `paths.cartographerJobsDir` in the workflowy_nexus JSON config, else the portable runtime default (`%LOCALAPPDATA%/workflowy-mcp/cartographer_jobs` on Windows; platform-equivalent state home elsewhere). **Never reconstruct this path independently from `%LOCALAPPDATA%/workflowy-mcp`** — that is the parent runtime directory, not `jobs_root`; omitting the final `cartographer_jobs` component would split claims/governor state from the live job JSONs and fail governance open.

**The scoping rule (one sentence):** region safety state (claims, tombstones, sentinels, heartbeats, admission mutex) is **machine-wide** because disk paths are machine-global truth; write pacing state (governor, breaker, write-slot mutex) is **account-scoped** because WFB(3) and API quotas are per-account.

`account_scope_id = sha256(canonical_json([normalized_api_base_url, api_key]))[:32]` — computed at client init from credentials the process already holds; the raw key is never persisted. The base URL is normalized first: trim whitespace, lowercase scheme and host, strip trailing `/` characters, and drop the default port for the scheme (`:443` for https, `:80` for http). No browser/broker account discovery is needed. If two runtime dirs are deliberately configured differently, they are simply separate coordination domains (accepted, not engineered around).

**Canonical hash encoding (all governance hashes, one rule, no exceptions).** Every multi-field sha256 in this spec — `account_scope_id` (above), `artifact_key` (below), and `dedupe_key` (§6.6) — hashes the UTF-8 encoding of a **canonical JSON array** of its normalized ingredients (compact separators, `ensure_ascii=False`, fixed field order as specified per key) — never ad-hoc concatenation of variable-length strings. Single-input hashes (`region_key` from a path or `"uuid:"+root_uuid`) hash the single normalized UTF-8 string directly. There is exactly ONE encoding rule across the whole spec; no hash in this document uses any other scheme.

```
<jobs_root>/                              (= get_cartographer_jobs_dir(), exactly;
                                           configured paths.cartographerJobsDir,
                                           else .../workflowy-mcp/cartographer_jobs;
                                           byte-identical to
                                           _get_carto_jobs_base_dir())
  .refresh_claims/                       (existing — untouched)
  .refresh_locks/                        claims (machine-wide)
  .q3_leases/                            transient Q3 disk-mutation leases (machine-wide)
  .refresh_tombstones/                   cooldown records (machine-wide)
  .cancel_requests/                      cancellation sentinels (machine-wide)
  .heartbeats/                           worker heartbeats (Phase F)
  admission.mutex                        OS-locked; admission/finalize/GC transactions
  .governance/<account_scope_id>/
    write_slot.mutex                     OS-locked; ticket issuance + breaker transitions
    write_governor.json                  {"next_slot_at": epoch}
    write_breaker.json                   breaker state (see §5.4)
```

**Path derivation is algorithmic from the jobs root.** `jobs_root` = exactly `get_cartographer_jobs_dir()` / `_get_carto_jobs_base_dir()`: the resolved `paths.cartographerJobsDir`, else the portable `.../workflowy-mcp/cartographer_jobs` fallback. All machine-wide state lives directly under `jobs_root`; all account-scoped state lives under `jobs_root/.governance/<account_scope_id>/`. No module may infer a "runtime parent" (e.g. `%LOCALAPPDATA%/workflowy-mcp` or `../governance`): two deliberately distinct configured jobs directories are fully separate coordination domains by construction, and a single shared derivation prevents two modules from accidentally splitting one domain. Dependency-light modules receive `jobs_root` by argument or import the authoritative config helper; they never hand-build the fallback.

### Artifact keys (account-aware; cross-account path cooldown preserved)

Two layers are distinguished: a **region key** (pure region identity) and an **artifact key** (account-scoped filename component). The filename always carries the account scope so the same region under a different account never overwrites another account's claim or tombstone file.

```
region_key   = sha256(normcase(realpath(path))   if path present
                      else "uuid:"+root_uuid)     # 64-hex, no truncation
artifact_key = sha256(canonical_json([account_scope_id, region_key]))
```

- **Claim filename:** `.refresh_locks/<artifact_key>.<job_id>.lock.json` (job_id disambiguates co-claims).
- **Tombstone filename:** `.refresh_tombstones/<artifact_key>.json`.

> **Why this is safe for cross-account path cooldown.** Account-keying the *filenames* does NOT weaken cross-account disk-path protection, because the admission overlap check (§6.3) is a **predicate scan over every live claim and tombstone** — comparing `path` across all accounts — not a filename lookup. Distinct filenames merely prevent two accounts' tombstone metadata from overwriting each other. The cross-account rule lives in the overlap predicate (§6.2), not in the key.

**Claim** `.refresh_locks/<artifact_key>.<job_id>.lock.json`:

```json
{
  "claim_id": "hex-uuid4",
  "job_id": "carto-refresh-...",
  "job_type": "CARTO_REFRESH | CARTO_MARKDOWN_GENERATE | CARTO_BULK_APPLY",
  "dedupe_key": "sha256-of-normalized-launch-intent (see §6.6)",
  "account_scope_id": "...",
  "kind": "file | folder",
  "path": "canonical absolute path or null",
  "root_uuid": "...",
  "ancestor_chain": ["root_uuid", "...", "vault-side ancestor uuids"],
  "launcher": "agent | gui | system",
  "parent_job_id": null,
  "launched_at": "iso-utc",
  "launcher_pid": 1234,
  "pid": 1234,
  "pid_create_time": 1780000000.125,
  "handoff_state": "preparing | spawning | running",
  "spawn_started_at": "iso-utc | null",
  "execution_owner": "launcher | detached_worker"
}
```

`pid` + `pid_create_time` name the *current owner* (see §8's handoff: launcher during preparation/spawning, then the detached worker). **Schema requiredness (A-15):** every field in this example is REQUIRED on every claim — the three handoff/ownership fields included (initial values per §8's admission rows: F12+4 — `handoff_state="preparing"`, `spawn_started_at` null until C.1; plain detached launches — `handoff_state="spawning"` with `spawn_started_at` set at admission; `execution_owner="launcher"` in both). The §6.7 unclassifiable-artifact rule treats a claim missing any required field as schema-invalid (fail closed); a writer built from this example and a validator built from the §8 prose must never diverge. **The claim file is the SINGLE liveness/kill-verification authority for owner identity** — the job JSON's `pid` mirrors it for presentation/diagnostics only and is never consulted to decide a reap or a kill. The claim's owner fields are rewritten only under `admission.mutex`: at claim creation (launcher identity), at the conditional post-`Popen` child-PID record, and at worker claim-adoption (§8) — and each of the three writes all four owner fields from ONE `ProcessIdentity`, never a partial re-stamp. **Owner identity (U01):** `pid_create_time` is now write-only provenance, never consulted as authority. Every claim additionally carries the additive-optional stable-identity pair `pid_start_ticks` (Linux: `/proc/<pid>/stat` field 22, unsigned clock ticks since boot; Windows: the kernel creation time as an exact 100-ns integer) and `pid_boot_id` (Linux: `/proc/sys/kernel/random/boot_id`; Windows: null) — this clock-independent pair is the PID-identity anchor used by liveness and force-kill verification, compared EXACTLY as integers/strings with NO epsilon. Claims written before U01 lack the pair (legacy) and fail closed: never reaped while their pid exists, and self-authority (kill verification, adoption) decides on pid equality plus the artifact's own pre-existing proofs.

**Status/type vocabulary mapping (stated once):** the claim file's `job_type`, the job JSON's `type`, and the scanner's presented `kind` all carry the same `CARTO_*` value; map between them at each artifact boundary and never proliferate a fourth spelling. The claim additionally carries `handoff_state` (`preparing` | `spawning` | `running`) and `spawn_started_at`, mirrored to the job JSON's `status` — the claim is the authority the §6.3 sweep consults, the job JSON the presentation copy. **Job-identifier key mapping (stated once, R12):** the persisted job JSON carries its identifier under the **`"id"`** key; the claim file carries it under **`"job_id"`**; the scanner's presented record emits **`"job_id"`**. When the spec says "parse the `job_id` from the job JSON" (R7), the actual key is `job["id"]`. Map between `"id"` and `"job_id"` at each artifact boundary and never proliferate a third spelling.

**Tombstone** `.refresh_tombstones/<artifact_key>.json` — carries the **full footprint** (path, root_uuid, ancestor_chain, kind, account_scope_id, dedupe_key) so the overlap predicate runs on tombstones exactly as on claims, plus `{"last_terminal_at", "job_id"}`. Write-merge rule: `last_terminal_at = max(existing, now)` so a parent finalizing after its child can never regress the cooldown clock.

**Sentinel** `.cancel_requests/<job_id>.cancel` — existence is the signal; content `{"requested_at", "requested_by"}`.

**Q3 lease** `.q3_leases/<artifact_key>.<lease_id>.lock.json` — see §6.8. Transient; reaped on owner-PID death with NO tombstone (no cooldown). **Naming warning (R8):** `.q3_leases/` and `.refresh_claims/` (the pre-existing terminal-refresh idempotency markers) are UNRELATED directories with OPPOSITE lifecycle rules — `.refresh_claims` is age-swept aggressively by existing GC; `.q3_leases` must never be. Do not widen the existing `.refresh_claims` glob patterns onto any new directory.

**Heartbeat** `.heartbeats/<job_id>.json` — static identity content written once at worker start (`{"pid","job_id","claim_id"}`); freshness = **file mtime** via `os.utime` ~1/s. Never rewrite the JSON per tick.

**GC** (extends `_gc_carto_jobs` / `_clear_carto_job_history`) — see §6.7. Reaps expired tombstones, dead-PID claims, sentinels and heartbeats belonging to terminal jobs with no live claim, and genuinely orphaned sentinels/heartbeats past an age threshold. Deny-by-default for anything unrecognized. Breaker/governor state files persist (tiny, self-describing).

> **Manual operator escape hatch.** Deleting `write_governor.json` and/or `write_breaker.json` is safe by construction: §4's corrupt-state rule self-heals an absent/malformed file by reinitializing it under its mutex. This is the documented manual override for a genuine server-side write block the operator wants to clear; it is loud (logged) and never automatic. It affects fresh acquires immediately. An already-issued anonymous ticket cannot be revoked safely, but §5.3's 30-second maximum caller wait bounds that residue; deletion never releases a multi-hour sleeper or wakes a ticket herd.

## 4. Shared primitives

- `os_lock(path)` — context manager over `msvcrt.locking` (retry loop) / `fcntl.flock`. OS-released on crash. Async paths: non-blocking attempts + cancel-aware async sleep between attempts (§2).
- **Busy vs. broken contract** (applies to both mutexes). Two distinct outcomes, never conflated:
  - **Busy** = the mutex is merely held by someone else. **Wait**, bounded and cancel-aware (≈ `governance.mutex_wait_seconds`, default 10 s — the normal case at ~1 acquisition/sec). If the bounded window expires while still *busy* (held, but the syscall itself is healthy), the result is a distinct loud **busy-timeout refusal** (`*_busy_timeout`) — no write is performed and no admission proceeds (still fail-closed) — but it is reported as *busy-timeout*, never as *broken*. Under the millisecond-hold invariant (§2) a busy-timeout should be unreachable in practice; it exists so a pathological holder degrades to a loud, named refusal rather than a silent hang.
  - **Broken** = the governance path cannot be created/opened, or the lock syscall itself errors. This **fails closed** with the loud error (`WriteGovernorUnavailableError` / `AdmissionUnavailableError`) naming the exact path.
  - **Errno taxonomy (A-6, normative):** ordinary contention on a NON-BLOCKING attempt surfaces as an `OSError` on BOTH platforms, so "syscall error ⇒ broken" is NOT decidable without errno inspection. Contention errors are BUSY, never broken: POSIX `fcntl.flock(LOCK_NB)` raising `EAGAIN`/`EWOULDBLOCK` = busy; Windows `msvcrt.locking(LK_NBLCK)` raising `EACCES`/`EDEADLK` (or the platform would-block equivalent) = busy. Open/create failures and every OTHER lock-syscall error = broken → fail closed. Implementing "syscall error ⇒ broken" literally would fail the system closed on its own routine contention.
  - **Per-attempt handle discipline (A-6):** each acquisition attempt opens its OWN file handle; a shared module-level handle is forbidden (OS locks are per-handle/per-process and not reentrant — two asyncio tasks in one MCP process, e.g. two Q3 batches or a Q3 batch and a launch, must contend on equal terms). On Windows the mutex file must contain ≥ 1 byte: open, `seek(0)`, lock exactly that byte, unlock the same range, then close. Cancellation or busy-timeout closes the pending handle. Real-subprocess tests cover contention classification.
  - *Busy never errors-as-broken; broken always fails closed.*
- **Corrupt state ≠ broken path.** A corrupt JSON state file (governor/breaker) is quarantine-renamed and reinitialized under its mutex (self-heal; worst case is a few writes landing closer together). An unwritable directory is broken → fail closed.
- Atomic JSON writes: temp file + `os.replace` (the `merge_write_carto_job_status` precedent). **This applies to claims and Q3 leases specifically (R3):** all claim/lease/tombstone/sentinel writes are atomic-replace writes, even though every *mutation* is mutexed — because the 1 Hz scanner and any read-side consumer reads these files WITHOUT the mutex. An in-place write would hand lock-free readers torn JSON, which then fail-closed-blocks admission as `governance_state_unclassifiable` (a self-inflicted refusal). Atomic write ⇒ lock-free reads are always of a complete file.
- **The pre-existing `/nodes-export` snapshot-patch lock is inventoried and intentionally left separate (v13).** `WorkFlowyClientCore._nodes_export_snapshot_lock` guards `patch_nodes_export_snapshot_on_disk` with an `O_CREAT|O_EXCL` claim file, 30 s age-based stale takeover, and fail-open behavior on lock failure. F12+4/F12+5 preparation uses this path for its read-latest → narrow patch → atomic snapshot rewrite. This is **cache-consistency coordination only**, not region ownership and not mutation authority: its worst failure is stale/lost cache patching, later repaired by freshness/reconcile; it never authorizes overlapping source or Workflowy mutations. Therefore its age-based takeover and fail-open policy are accepted unchanged, but they are NEVER copied into `admission.mutex`, claims, Q3 leases, or any governance artifact. The separate `.refresh_claims/` terminal-refresh idempotency markers are likewise not region leases; their existing fail-open duplicate-refresh fallback remains bounded and untouched.
- **Markdown parser purity + explicit C0 repair (v10).** `parse_markdown_structure` and every snippet/dry-run/read helper sanitize illegal Markdown C0 controls **in memory** before tokenization so line maps remain correct, but they NEVER write source bytes. This includes `beacon.snippet` MD_PATH resolution and the Windsurf `refresh_file_node_beacons(dry_run=True)` fallback: both remain byte-for-byte disk reads. Persisting a repair is a separate named mutation primitive (e.g. `repair_markdown_c0_controls_on_disk`) invoked only while a claimed CARTO owner holds the target region, before its authoritative parse/reconcile. That repair writes atomically (same-directory temp + flush/fsync + permission copy + `os.replace`), logs the repaired control kinds/count and path, and is cancellation-aware before commit. A parser is never a writer; a dry run is never a writer; the cleanup benefit is preserved under explicit region ownership.
- **psutil is a new hard dependency** — PID liveness, creation time, and command-line identity in ~20 lines, portable.
- Governor clock: wall-clock epoch persisted; a FORWARD NTP jump can make at most one ticket appear due early before persisted spacing resumes, while a BACKWARD jump merely extends the wait — bounded and accepted (comment, not engineering). The same direction intuition applies to breaker deadlines: forward can expire early; backward can extend.
- **Job-scoped cancellation context.** Detached workers install a client-level cancel callback today; inside the MCP server process many unrelated requests share one client object, so in-process governed jobs (`CARTO_BULK_APPLY`, F12+4/F12+5 preparation, F12-on-AST preparation) must supply a **job/task-local** cancellation probe (e.g. a `contextvars.ContextVar`) to governor slot waits, mutex waits, and retry/backoff sleeps — never a shared-client-global callback. Cancelling one bulk job must not interrupt an unrelated tag edit on the same client. **Composition with the injected sleeper (explicit):** the governor's `sleep_fn` (§5.2 step 1 passes `self._sleep_with_operation_cancel`, which polls the client-level `_operation_cancel_callback`) must consult BOTH probes — the injected client-level callback AND the ambient job-scoped `ContextVar` probe — raising when either fires. Detached workers have only the client-level callback (the contextvar is unset); in-process jobs have the contextvar set. This is how §5.2's pseudocode and this bullet reconcile: wiring only the client-global callback would leave in-process job cancellation unimplemented.
- **The legacy in-process `AdaptiveRateLimiter` layer is subsumed, not resurrected (F2).** `server.py` instantiates a module-level `AdaptiveRateLimiter` (~line 9321), calls `_rate_limiter.acquire()` at ~33 tool entry points, and feeds it `_rate_limiter.on_rate_limit(getattr(e, "retry_after", None))` at ~30 catch sites. Today its retry-after axis is inert ONLY because of the very `retry_after`-attribute bug Phase 0 fixes: `getattr(e, "retry_after", None)` is always `None`, so `set_retry_after` never fires. Phase 0's attribute fix would ACTIVATE it — a 429 honoring a 6-hour `Retry-After` would land in `set_retry_after`, and the next `acquire()` would sleep the full period **while holding `self.lock`** (verified: the sleep is inside `async with self.lock`), silently stalling EVERY subsequent tool call in the process — no state file, no inspection, no cancellation hygiene, no escape hatch: exactly the silent-wedge class principles 1–2 exist to kill. The fix (Phase 0, NOT Phase B — the hazard activates at Phase 0): **sever the `retry_after` propagation into `_rate_limiter`** (the write governor becomes the sole account-wide 429-defer authority) — remove the argument at the ~30 `on_rate_limit` call sites or make `on_rate_limit` ignore it with a loud deprecation comment. Optionally also move the `acquire()` retry-after sleep outside the lock. The token-bucket local pacing itself may stay (inert under the governor) but gains NO new role — and the severance removes ONLY the `retry_after` argument propagation: `on_rate_limit`'s rate-halving adaptation and the bucket itself STAY byte-for-byte (do not sever the whole method or "clean up" the halving). (Pre-existing nuance, correcting §0's narrative: `retry.py`'s `RetryHandler` already reads `e.details.get("retry_after")` and honors the header today — "silently ignored" is true only of the CRUD `getattr` loops; `api_client_etch.py`'s `/nodes-export` loop also reads `details["retry_after"]` but LOGS IT ONLY and keeps exponential read backoff. The full consumer list after the Phase-0 fix is therefore: CRUD loops (intended, subject to the 30 s caller-wait bound), `retry.py`'s `RetryHandler` (source-verified UNWIRED; do not newly wire it as a second write retry/defer layer, and any future use inherits the same 30 s local ceiling), `api_client_etch.py` (log-only — do not turn it into server-duration read sleep), and the ~30 `_rate_limiter.on_rate_limit` sites (the severed hazard).)
- **The legacy pre-flight coordination layer is SPLIT, not kept whole (S10 + S11, v13 corrected inventory).** `_handler_preflight_cache_quiescence` (server.py) fuses TWO roles but is **not** currently called by every outermost F12 handler. Its verified live callers are the shared FILE/AST refresh handler, F12+3 generate, and standalone F12+2 bulk apply; the FOLDER handler only awaits an already-running nodes-export refresh and does NOT force freshness, while F12+4/F12+5 historically use snapshot patching instead of this preflight. Role (1) is `_await_carto_jobs_quiescent` — a machine-wide, status-derived wait until `_carto_active_cache_jobs` drains to zero (the pre-claims region-safety approximation). Role (2) is a forced, awaited /nodes-export refresh (~30–60 s, rate-limited) — the DATA-FRESHNESS guard whose own docstring names the hazard: a stale ether tree can make reconcile silently drop the user's recent Workflowy edits in OTHER nodes of the same file. A user-controlled cross-process skip toggle (`_cache_refresh_should_skip`) bypasses both today. v13 rules the layer explicitly. **Role (1) is RETIRED as a launch/mutation gate:** claims + Q3 leases + the overlap predicate are the ownership authority; the global barrier is redundant with them AND contradicts §6.2's non-overlapping parallelism (a repo-B launch must not wait for repo-A's refresh to drain). Removal is safe because the incoming claim guarantees no live system-managed mutation overlaps the target footprint — a snapshot taken while a NON-overlapping job mutates elsewhere is consumed only within the claimed footprint, and later work on that other region performs its own freshness step (§6.2's accepted bounded drift covers the rest). **GENERAL DOCTRINE (generalizing the §7.1 bulk-apply fix): no coroutine may await CARTO-jobs quiescence while its own job JSON is active** — the prepared-launch background task's own `preparing` job JSON is ACTIVE and `cache_refresh_required=True`, so awaiting global quiescence there would deterministically deadlock on itself. **Role (2) — the freshness refresh — is KEPT, corrected, and explicitly placed** (§6.5/§8 B.0): prepared launches run it uniformly inside the claimed background task, after admission, before preparation; this knowingly changes the historical F12+4/F12+5 refresh-skipping fast path, but preserves immediate acknowledgment and coalescing. Plain FILE launches keep their pre-admission forced refresh. Plain FOLDER launches now **ADD** the same pre-admission forced refresh — there was no existing call to preserve. F12+3 and standalone F12+2 retain pre-admission freshness while dropping only CARTO-global quiescence. A freshness failure after admission is a post-claim failure through the one exit door. **Skip-toggle rule:** the toggle may skip FRESHNESS reads only; it NEVER skips claim admission, lease overlap detection, the governor, the breaker, worker adoption, or finalization. The /nodes-export refresh coordination machinery itself (`_await_nodes_export_cache_quiescent`, the coalescing queue, terminal-job cache-refresh batching, `_carto_active_cache_jobs` as presentation state) is untouched — only its use as a PREREQUISITE for admitting or executing another independent mutation is removed; once the last gate call is gone, `_await_carto_jobs_quiescent` may be deleted as dead code, never repurposed as a gate.

**Closed freshness authority (v14).** The prose above explains the mechanism; §18 is the normative closed origin matrix. Freshness is a property of the normalized launch type, never of whichever WS/MCP transport happened to call it. If any earlier caller-specific sentence appears broader or narrower than a §18 cell, §18 wins. The user skip toggle skips only the designated freshness read; it never authorizes a detached worker to invent a replacement refresh.

### 5.2 One send authority

Introduce `async _send_workflowy_write(method, url, **kwargs)` in `api_client_core.py`. All six sites route through it (their per-iteration `API_RATE_LIMIT_DELAY` sleep lines are **removed** — the governor replaces the per-process delay; no double-pacing; the constant survives only as the documented pre-governor default in comments/config fallback). The authority **sends and returns the raw `httpx.Response`**; `_handle_response` remains the ordinary response-to-exception/data mapper.

> **Preserving the still-waiting diagnostics.** `create_node` wraps its `self.client.post(...)` / `self.client.get(...)` calls in an `asyncio.create_task` + `asyncio.wait_for(..., timeout=10.0)` loop to emit periodic "still waiting (elapsed …)" diagnostics. The authority must support an equivalent pattern (behavior, not necessarily the literal `wait_for` code). The cleanest shape: the authority accepts an optional progress/diagnostic hook (or the call site passes its own label) so the "still waiting" warnings survive around the send. The trailing `GET /nodes/{id}` after **create AND update** (F-9: `update_node` also issues a trailing read after its POST, verified `api_client_core.py:~2012`) is a read and stays outside the governor.

Before returning, the authority inspects the response status *for governance only*:

```
1. await governor.acquire_write_slot(op_label, sleep_fn=self._sleep_with_operation_cancel)
2. re-check breaker under write_slot.mutex (a reservation issued before a trip must not fire).
   The recheck PASSES when the breaker is `closed`, OR `half_open` with
   `probe_claim_id == mine` (the probe holder's own reservation IS the probe);
   it blocks every other reservation while the breaker is open or half_open.
   **A blocked recheck raises `AccountWriteBlockedError` (R1):** the
   `retry_after` is `max(0, blocked_until - now)` when open, `max(0,
   probe_lease_expires_at - now)` when half_open; no write is performed
   (fail-closed, identical to the pre-ticket blocked path). When the
   relevant deadline is ALREADY in the past (an expired deadline on an
   already-issued reservation), `retry_after` floors at 0 and the teaching
   text tells the caller to RETRY the operation as a fresh acquire — the
   fresh acquire can then claim the probe (A-10).
3. send the request
4. notify outcomes (probe-token verified where applicable — see §5.4):
   2xx            → breaker.close_probe_verified(mine)
   429            → if this was the half-open probe:
                       under ONE write_slot.mutex hold, token-verify and close
                       the WFB probe AND max-merge the global Retry-After defer
                       (endpoint answered; WFB is no longer governing). This is
                       ONE combined already-locked transition — never two public
                       acquiring helper calls with a fresh-ticket gap between.
                    else:
                       governor.defer_global_writes_until(retry_after)
                    parse per §5.3; then the EXISTING bounded retry path proceeds
   403 WFB(3)     → atomically trip/re-trip the breaker (see 5.4), then RAISE
                    AccountWriteBlockedError for the TRIGGERING caller, populated
                    from the newly persisted generation (A-9) — the WFB response
                    does NOT return to ordinary _handle_response mapping, so the
                    caller always receives the account-block teaching error (and a
                    matching half-open probe gets the recovery-probe teaching text).
                    A NON-WFB 403 (and every other status) returns normally for
                    ordinary mapping.
   other 4xx      → if this was the half-open probe: breaker.close_probe_verified(mine)  [endpoint answered]
   5xx            → if this was the half-open probe: breaker.reopen_probe(mine, bounded)
   timeout/network during half-open probe → breaker.reopen_probe(mine, bounded)
```

This removes the v3 ambiguity between "governance in the authority" and "governance in `_handle_response`": **all governance outcomes live in the sole send authority.**

**Static enforcement:** a registration-style AST-walk test rejects any direct mutating call on the httpx client outside `_send_workflowy_write`: convenience verbs `.post/.delete/.put/.patch`, generic `.request(...)` when the method can be mutating, and low-level `.send(...)` of a mutating request. AST, not grep, so comments/strings do not false-positive and a future transport refactor cannot walk around the fence by changing call shape. **Fence-shape and scan-scope pins (v13):** the HTTP fence matches by METHOD-NAME CALL SHAPE (attribute-calls `.post(/.delete(/.put(/.patch(/.request(/.send(` plus module-level `httpx.<verb>(...)`) within the client-module scan, allow-listing only the send authority — it must NOT attempt receiver-type inference (statically undecidable). EVERY static fence in this spec (this one, the §6.5 reconcile allow-list, and the §9 parser write-open test) discovers runtime source from the repo source tree ONLY — `src/` plus all FIVE importable repo-root runtime modules: `beacon_mutation_contract.py`, `beacon_obtain_code_snippet.py`, `glimpse_deploy_trampoline.py`, `markdown_roundtrip.py`, and `nexus_map_codebase.py` — and EXCLUDES `.venv/`, test fixtures, scripts, and generated copies. The venv contains stale NON-editable copies of these root modules (including `nexus_map_codebase.py` still carrying the parser's deleted C0 write), which would otherwise false-positive or falsely satisfy a fence. The prior four-module list was incomplete: omitting `beacon_mutation_contract.py` would leave the claimed future call-graph seal structurally open.

### 5.3 acquire_write_slot

The breaker decision and ticket issuance are **one critical section** under `write_slot.mutex`. **Probe availability is defined exactly:** the half-open probe is *available* iff `probe_claim_id` is absent/null **or** `probe_lease_expires_at <= now` (a lapsed lease frees the slot for another process). The pseudocode's "probe unclaimed" below means exactly this availability test.

```
with os_lock(write_slot.mutex):                       # milliseconds
    b = read(write_breaker.json)
    if b open and not expired:
        raise AccountWriteBlockedError(retry_after = max(0, blocked_until - now), reason)
    if b open_or_half_open and probe_claim_id present and probe_lease_expires_at > now:
        # another process holds the live half-open probe. STATE-AGNOSTIC guard
        # (A-10): the probe FIELDS, not the state word, decide — an expired-open
        # breaker with a live claimed probe still blocks every other writer here,
        # in the PRIMARY guard (the §5.2 recheck stays belt-and-suspenders).
        raise AccountWriteBlockedError(retry_after = max(0, probe_lease_expires_at - now))
    if b expired (or half_open) and probe available:  # probe_claim_id null or lease lapsed
        atomically claim the half-open probe           # THE CLAIM WRITE PERSISTS
                                                       # state="half_open" + probe_claim_id +
                                                       # probe_lease_expires_at IN THE SAME
                                                       # ATOMIC WRITE (A-10): the expired-open
                                                       # → half_open transition happens AT
                                                       # CLAIM TIME, here — not implied by §5.4.
    s = read(write_governor.json); now = time()
    my_slot = max(now, s.get("next_slot_at", 0))
    slot_wait = max(0, my_slot - now)
    if slot_wait > MAX_WAIT_BEFORE_REFUSAL:                 # config, default 30 s
        raise WriteGovernorDeferredError(retry_after=slot_wait)  # NO ticket/state advance
    s["next_slot_at"] = my_slot + INTERVAL                 # config, default 1.0 s
    atomic_write(s)
await sleep_fn(max(0, my_slot - time()), op_label)    # injected, cancel-aware
return slot_token (probe_token if half-open claimer)
```

- Two processes can never independently observe an unclaimed half-open state: claim, decision, and ticket are atomic together.
- **Bounded caller wait, then loud refusal (v11).** Still inside the same critical section, after computing `my_slot` but BEFORE advancing `next_slot_at`, calculate `slot_wait = max(0, my_slot - now)`. If `slot_wait > write_governor.max_wait_before_refusal_seconds` (default 30 s), issue NO ticket and leave `next_slot_at` unchanged; raise `WriteGovernorDeferredError(retry_after=slot_wait, deferred_until=my_slot, reason="global write slot is beyond the bounded caller-wait window")`. This is distinct from mutex busy-timeout and from the WFB breaker: the governor remains healthy, but an interactive caller must not become an uncancellable multi-hour coroutine. Ordinary one-second pacing and modest reservation queues still wait normally. The account-wide `next_slot_at` retains the FULL valid server defer — this refuses a caller rather than downward-clamping the server instruction.
- **Triggering 429 local retry uses the same bound — in ALL EIGHT CRUD retry loops (v12).** The Phase-0 `retry_after` attribute fix activates the identical dormant `getattr(e, 'retry_after', None)` branch in the two READ loops (`get_node`, `list_nodes`) exactly as in the six write loops; unbounded, a read 429 carrying a valid multi-hour `Retry-After` becomes an uncancellable multi-hour `get_node`. The ceiling therefore applies to EVERY CRUD retry loop, reads included — reads never touch the governor, and past the bound they re-raise exactly like writes. The CRUD loop may sleep/retry only when its selected local retry delay is ≤ the configured bound (Phase 0 uses a hardcoded 30 s until Phase B wires the key). If a valid `Retry-After` exceeds it, re-raise the original `RateLimitError` immediately after the send authority has persisted the full global defer; do not sleep for hours. `Retry-After: 0` retains §5.3's exponential-local-delay rule. This changes caller waiting, never the account-wide defer.
- **Manual-override precision.** Deleting governor/breaker JSON affects fresh acquires immediately. Already-issued sleepers are not anonymously revocable, but the bounded-wait rule limits that residue to at most the configured 30 s; a periodic state reread is neither required nor safe (tickets have no durable per-ticket identity, so treating deletion as revocation could wake multiple holders together).
- Crash between ticket and write wastes one slot — safe by construction.
- **Fail closed:** if the governance dir/state cannot be written (per §4 busy/broken), raise `WriteGovernorUnavailableError`; **no write is performed.** There is no fallback to per-process delay — that would recreate the incident's multiplication exactly when the substrate breaks.
- **Half-open probe lease:** when a probe is claimed, the claim carries `probe_lease_expires_at = now + write_governor.probe_lease_seconds` (§12). While a probe is claimed and unexpired, other writers get `AccountWriteBlockedError` with `retry_after = max(0, probe_lease_expires_at - now)` (the probe-lease deadline — `blocked_until` has already passed, so the lease is the meaningful deadline).
- **429 → global defer (strict parse, honor valid, conservative fallback on malformed).** On `RateLimitError`, the server-provided `retry_after` bumps `next_slot_at` account-wide under the write-slot mutex, so *all* processes honor the server's requested pause.
  - **The defer is a monotonic max-merge (F-1):** `next_slot_at = max(existing next_slot_at, now + parsed_retry_after)`. A defer NEVER moves `next_slot_at` earlier. This is the same max-merge doctrine §3 already mandates for tombstone `last_terminal_at`, applied to the governor: without it, a short defer landing behind a long already-issued reservation queue would regress the clock and let fresh tickets interleave with pre-defer reservations, transiently exceeding one write per interval.
  - **Parse — ONE shared helper (A-7):** `parse_retry_after_header(raw_header, now_epoch) → {delay_seconds, used_fallback, diagnostic}` is the single grammar authority for both RFC forms — (a) nonnegative delta-seconds, (b) an HTTP-date converted to a nonnegative delay — plus missing/blank/malformed/negative/non-finite. Phase 0's `_handle_response` fix AND Phase B's governor defer both consume it; there must not be two hand-written parsers. The current source does `int(retry_after) if retry_after else None` — an HTTP-date form raises an **unhandled `ValueError`** instead of producing a `RateLimitError`. Fixed in Phase 0.
  - **Zero semantics (A-8):** `Retry-After: 0` is a VALID parsed value, distinct from absent. `RateLimitError.__init__` sets the attribute even when it is 0 (the current `if retry_after:` truthiness gate drops it — Phase 0 fixes). A zero defer is a no-op max-merge on the governor (`now + 0` can never move `next_slot_at`). The local CRUD retry loop still applies its conservative exponential backoff on a zero (an immediate in-loop retry adds no safety value); both behaviors are pinned here, never inferred from Python truthiness.
  - **Honor valid values exactly — NO downward clamp.** If Workflowy says "don't write for 6 hours," the system defers 6 hours. Safety favors honoring a genuine server instruction over second-guessing it. The manual override (delete the state file, §3) is the documented escape hatch, not an arbitrary clamp.
  - **Missing, blank, malformed, negative, or non-finite (A-4):** a 429 with **no** `Retry-After` header (or an empty one) is treated identically to a malformed one — log loudly with the raw header and use the conservative fixed fallback (`write_governor.retry_after_fallback_seconds`, default 60 s). Never reinterpret absent or malformed data as a huge epoch/duration, and never apply no defer at all.
  - **Every global defer logs loudly:** raw header, parsed delay, resulting `next_slot_at` (UTC), account-scope prefix, triggering operation. The JSON state is directly inspectable; waiting tool calls remain cancellable.
  - (Companion fix, Phase 0: `RateLimitError.__init__` must actually set `self.retry_after` — today it only lands in `details`, and the CRUD catch blocks read the attribute, so the header is silently ignored.)
- **Accepted bounded leakage (do not engineer away):** tickets issued *before* the 429 still fire — but they were issued by the single global governor, so they proceed at ≤ 1 write/interval and cannot recreate the incident's multiplication. No reservation-recall machinery.
- **Probe teaching error:** when the half-open probe fails with WFB(3) again, the error to that caller says "your write was the recovery probe; the account is still blocked until …".

### 5.4 Circuit breaker (`write_breaker.json`)

States: `closed → open → half_open → closed/open`. Fields: `state, blocked_until, cooldown_s, probe_claim_id, probe_lease_expires_at, reason, evidence_excerpt`. **Every breaker read-modify-write transition happens under `write_slot.mutex`** (same lock as ticket issuance; ms hold times; no third lock).

- **Trip:** in the send authority's 403 branch, pattern-match the retained body for `WFB(3)` → write `open` state. Loud `log_event`; surfaced in job errors and tool error envelopes ("account write-block detected; writes suspended until …").
- **Open:** every `acquire_write_slot` raises `AccountWriteBlockedError` locally — zero network traffic. Initial cooldown 900 s (config).
- **Expiry → half-open:** exactly one process atomically claims the probe (`probe_claim_id` + lease) inside the §5.3 critical section. Every other writer keeps refusing/waiting. Outstanding pre-trip reservations are suppressed by the §5.2 step-2 recheck.
- **Probe outcome table (exhaustive; every transition except an unconditional new WFB trip is verified against `probe_claim_id` — a stale probe response never closes or reopens a newer breaker generation):**

| Probe result | Breaker action |
|---|---|
| 2xx | close (WFB recovery confirmed) |
| 429 | under ONE `write_slot.mutex` transaction, **close** the token-matching WFB probe (endpoint responding) + max-merge the global rate-limit defer per §5.3; no fresh-ticket gap |
| WFB(3) again | open with doubled cooldown (cap 7200 s) |
| Other 4xx (incl. non-WFB 403) | **close** the WFB breaker (endpoint answered; WFB not governing); then let ordinary `_handle_response` mapping fail the request |
| 5xx | open with bounded probe-failure cooldown (a probe that got a server error is not evidence of health) |
| Timeout / network error | open with bounded probe-failure cooldown (no answer ≠ health) |
| Probe-process death / no result | lease expiry lets another process claim half-open later |
| Probe holder cooperatively cancelled before send (F5) | probe abandoned; **lease expiry** releases the claim — account-wide writes stay refused until the 120 s lease lapses (bounded, accepted). A proactive probe-release-on-cancel is NOT permitted (it would reopen the one-probe invariant to a release/reclaim race). |

  *Rationale for the "close on 429 / other 4xx" rows:* the WFB(3) breaker exists to suppress one specific account-level write-block. A probe that receives 429 or a non-WFB 4xx proves the endpoint is answering and the WFB block is no longer the governing constraint for that request — so the WFB breaker closes, and the ordinary rate-limit / error handling takes over. This is distinct from the *rate-limit* defer, which is a separate mechanism (§5.3).

- **A WFB(3) arriving while the breaker is NOT `closed`** (a stale pre-trip reservation, an in-flight write, or a non-matching probe response): never shortens `blocked_until` and never multiplies the cooldown repeatedly. Rules: `closed` + WFB → `open` at the initial cooldown; `half_open` + WFB from the *matching* probe (`probe_claim_id` verified) → `open` with doubled cooldown (cap 7200 s); `open` + WFB → keep the current generation (update `evidence_excerpt` if useful), no re-doubling, `blocked_until` never moves earlier; `half_open` + WFB that does *not* match the live probe claim → the account is evidently still blocked: transition to `open` at the CURRENT (un-doubled) cooldown for that generation. Multiple stale WFB responses against one generation therefore cannot compound the cooldown.
- **Accepted bounded race:** a write already in flight — or one that passed its final breaker check immediately before another request trips the breaker — cannot be recalled. The breaker suppresses future sends; it cannot unsend network traffic.
- **Drift tripwire:** any 403-on-write that does *not* match `WFB(3)` is logged at breaker-adjacent loudness, so a body-pattern change by Workflowy is noticed in one incident, not three.
- **`AccountWriteBlockedError` propagation:** a non-retryable sibling error (not a `NetworkError`). The existing CRUD retry loops (which catch `RateLimitError` / `NetworkError` / `httpx.TimeoutException`) must **not** catch or re-wrap it; it propagates out of the loop — with ZERO HTTP calls made when raised pre-send (a blocked acquire or step-2 recheck), or after exactly the ONE triggering send when raised by the §5.2 WFB branch (A-9). Locked by an explicit CRUD-level test.

## 6. Component: Job admission and claims (`src/workflowy_mcp/carto_job_governance.py`)

### 6.1 Footprint

`compute_footprint(path_or_none, root_uuid, cache_by_id)`: canonical normalized real path (or `None` for the temp regime) + `root_uuid` + **ancestor chain captured at claim time** from the /nodes-export cache. **Fail closed** if the chain cannot be resolved (refusal kind `footprint_unresolvable`, teaching text: run `system.cache.refresh` and retry) — consistent with the anchor-dock root-guard precedent. Footprint reads the CURRENT cache at admission time; the freshness refresh runs per the §4/§8 placement (prepared launches: B.0 inside the background task; plain launches: pre-admission), and §6.2's accepted bounded staleness covers the gap. For F12+4's very-fresh-node case, the footprint may be computed against the exact payload-overlaid `nodes_by_id` map the handler already builds (§8).

### 6.2 Overlap predicate (machine-wide paths; account-scoped graph)

Two footprints overlap iff **either**:

- both paths present and one is a path-prefix of the other (case-normalized `os.path.commonpath`, Windows-aware) — compared across **all** claims regardless of account. **Cross-drive / cross-volume pin (A-5):** `os.path.commonpath` raises `ValueError` for paths on different Windows drives/volumes; that branch is pinned as **no disk overlap** (different drive ⇒ disjoint trees by definition). Any OTHER unexpected path-normalization failure (not the distinct-drive case) remains fail-closed and loud, **or**
- `account_scope_id` matches **and** the graph footprints intersect, tested symmetrically: for the two claims A and B, A's `root_uuid ∈ (B's ancestor_chain ∪ {B's root_uuid})` OR B's `root_uuid ∈ (A's ancestor_chain ∪ {A's root_uuid})`.

The disk check catches same-repo collisions (including across accounts, since two accounts writing the same disk path race on real files); the graph check catches the Markdown-in-Markdown/temp-file case, and is same-account-only because a Workflowy node graph is per-account truth. Non-overlapping targets run freely in parallel (the 4-repo routine; writes are globally paced by §5).

**Accepted bounded race (documented):** `ancestor_chain` is captured at claim time. A node MOVED after its job's claim (or a chain captured from a stale cache) can make the graph-overlap check fail open — two jobs on regions that have since become nested could both be admitted. The path check still guards same-disk collisions; the residual is graph drift only, the window is the job's lifetime, and live graph re-validation per write is disproportionate. Accepted, not engineered.

### 6.3 Admission algorithm (per launch)

**PID-liveness truth table (A-1, normative; the ONE classifier used for claims AND Q3 leases everywhere in this spec; U01 form — clock-independent, exact comparison, no epsilon):**

| Identity observation | Classification |
|---|---|
| PID absent (no such process) | `dead` |
| Identity unreadable (procfs race, permissions, psutil error) or current `start_ticks` unprobeable | `unknown` — treated as `alive` (deny-by-default); never reaped, never killed |
| Stored `start_ticks` absent (LEGACY pre-U01 artifact) | `unknown` — the epoch `pid_create_time` is NEVER consulted |
| Stored `start_ticks` present and ≠ current `start_ticks` | `dead` — the original identity has exited and the PID number was recycled onto a different incarnation |
| Stored and current `boot_id` both present and ≠ | `dead` — different boot |
| Stored stable fields present and all compared fields equal | `alive` |

The shared sweep (and every other liveness consumer) consults this ONE table. **Force-kill additionally requires the exact `--carto-job-file` argv match (§7.3); liveness alone never authorizes a kill.** A `dead` classification alone (without spawn-grace) is what authorizes a reap.

Footprint is computed **before** the mutex (cache reads need no lock). Then:

```
with os_lock(admission.mutex):                       # machine-wide; ms hold
    sweep: for each active claim →
           UNCLASSIFIABLE claim (unparseable JSON, invalid schema, undecodable
               footprint) → treat as a LIVE, GLOBALLY CONFLICTING claim:
               refuse admission with governance_state_unclassifiable naming the
               exact artifact path; NEVER auto-quarantine, skip, or delete it (§6.7).
           liveness is decided from the CLAIM's owner identity (pid +
               the pid_start_ticks/pid_boot_id stable pair) — NEVER from the
               job JSON's pid mirror — via the A-1 truth table above:
             owner classified DEAD (PID absent, present-with-mismatched
               start ticks, or different boot)
               AND NOT (claim.handoff_state == "spawning" AND
               now - claim.spawn_started_at < spawn_grace)
               → REAP VIA finalize_claim_locked (§7.4 — the ALREADY-LOCKED
                 variant, A-12: the sweep holds admission.mutex; calling the
                 acquiring wrapper here would self-deadlock): if the persisted
                 job status is
                 NON-terminal, persist failed ("worker process vanished (pid N)")
                 via merge_write_carto_job_status — or cancelled when a sentinel
                 is present; if the persisted status is ALREADY TERMINAL
                 (completed / completed_with_warnings / failed / cancelled),
                 write NO status — the reap only tombstones and releases the
                 claim. (A worker that persisted completed and then died before
                 finalize_claim is never retro-labelled failed.)
                 A reap routes through the ONE EXIT DOOR — never a bare claim delete.
             owner PID verified alive → leave untouched, regardless of a
               missing / pidless / corrupt job JSON. start_grace (30 s) is a
               PRESENTATION/DIAGNOSTIC window only (§7.1) — age alone is NOT
               death evidence and NEVER authorizes a reap.
             owner identity unknown / indeterminate → leave untouched
               (deny-by-default: unknown ≡ alive; the claim still blocks overlap)
    claimless-job gate (A-11, rollout seam): the §7.1 legacy/fallback
      classification runs inside this same transaction — any claimless
      NON-terminal CARTO job JSON classified ALIVE or UNKNOWN is a GLOBAL
      transient conflict: refuse admission with overlap_conflict identifying
      the legacy job, with teaching text (it predates governance; it must
      finish, be stopped manually, or become verifiably dead before governed
      mutations begin). Claimless JSONs carry no authoritative path/ancestor
      footprint, so deny-by-default widens the conflict to ALL regions —
      NEVER infer a narrow footprint and NEVER synthesize/retro-adopt a claim.
      A DEAD claimless job is terminal-ized by the fallback (no tombstone,
      no block). This gate protects the first-rollout window in particular:
      detached pre-v8 workers survive MCP restarts by design, bypass the
      governor, and would otherwise overlap freely with newly-governed jobs.
    decision table:
      active claim with IDENTICAL dedupe_key      → DedupeHit(existing job)
      overlap with ACTIVE claim (different intent) → REFUSE overlap_conflict
          EXCEPT validated parent_job_id (see 6.4)
                                   → ADMIT as co-claim
      overlap with any live TOMBSTONE & now - last_terminal_at < 60 s
          → REFUSE cooldown_active(retry_after=…)
          EXCEPT validated parent continuation → bypass tombstone only
    create claim file (claim_id = uuid4 hex, carries dedupe_key + footprint +
      handoff_state + spawn_started_at + owner identity fields)
    create the initial job JSON under the SAME mutex hold (carries claim_id,
      dedupe_key, footprint, account_scope_id, launcher, parent_job_id, status,
      and the PID-identity mirror fields — see §8): claim and job JSON are
      created as ONE admission DECISION transaction for mutex-taking peers.
      They are still TWO atomic file replacements, not an impossible multi-file
      atomic visibility transaction: a lock-free scanner may briefly observe the
      live launcher-owned claim before the job JSON appears and MUST tolerate it
      as a starting/claim-present record. A job-JSON write failure here finalizes
      immediately through `finalize_claim_locked` (§7.4 — this path ALREADY
      holds `admission.mutex`; it must never call the acquiring wrapper), then
      fails the launch. A crash between the two writes leaves a claim whose owner
      PID later authorizes the ordinary dead-owner reap; safety never depends on
      lock-free readers observing both files simultaneously.
spawn worker (for a prepared launch — F12+4/F12+5 or F12-on-AST — preparation
              runs FIRST, UNDER the claim but OUTSIDE the admission critical
              section, with the handoff states of §8)
on any post-claim failure → universal finalize (§7.4): terminal status +
              atomic tombstone-and-release
```

> **The sweep's reap routes through `finalize_claim`.** The steps above say "REAP VIA finalize_claim" explicitly. Earlier drafts of this spec described the sweep as "persist failed …, delete claim" — that wording risked being implemented as a bare claim delete, which would skip the tombstone and give a crashed worker's region zero cooldown (an immediate relaunch onto a partially-mutated region). Every reap path — the admission sweep here, the watcher loop, and the §7.5 startup sweep — goes through `finalize_claim` so the tombstone (cooldown) is always written. §16.1's One-Exit-Door diagram already shows this; the prose now matches it.

> **Reap-internal write ordering and failure semantics (R2, explicit).** A sweep reap performs two writes in a fixed order: **(1) the terminal status write** via `merge_write_carto_job_status` (failed/cancelled per the terminal-preservation rule above), **then (2) `finalize_claim`**. `merge_write_carto_job_status` NEVER raises and may return False (best-effort contract); a failed status write **MUST NOT abort the reap** — proceed to `finalize_claim` anyway with a loud diagnostic (region safety and the cooldown tombstone must never hostage on a presentation write). The residue of a failed status write is a claimless non-terminal job JSON, which the §7.1 claimless-job fallback rule (below) later terminal-izes; do not instead abort-and-wedge the claim.

Notes:
- **Claim + initial job JSON form one admission decision, not one filesystem object.** Admission competitors are serialized by `admission.mutex`; lock-free scanner/watcher readers may see the short claim-first/job-not-yet-visible window and classify it from the live claim owner (within `start_grace`, present as starting). They never treat that expected window as corruption or synthesize a second claim.
- **Dedupe vs. cooldown vs. overlap are distinct:** active + same intent ⇒ dedupe-return; active + different intent ⇒ overlap refusal; recently finished ⇒ cooldown refusal. Never conflate.
- **Dedupe key ≠ footprint.** Footprint answers "could these operations collide?"; dedupe key answers "are these the same request?" See §6.6.
- Same path, different mode (file vs folder) ⇒ overlap ⇒ refuse.
- Tombstone check scans **all** live tombstones with the overlap predicate, not just the exact key.
- Under co-claims, dedupe returns the active claim whose `dedupe_key` matches the incoming request (an incoming refresh matches the child refresh; an incoming regenerate matches the parent while it lives).

### 6.4 Co-claims (MARKDOWN_GENERATE → phase-8 post-flight refresh)

The F12+3 worker holds a **path-keyed claim for its entire lifetime**. Its phase-8 post-flight CARTO_REFRESH launches with `parent_job_id` set; admission admits it as a **second claim on the same footprint**. No ownership transfer, no rollback state machine:

- **`parent_job_id` privilege is validated, not nominal — and the validation is the EXACT continuation edge, not mere overlap:** a continuation is honored only when ALL of: an *active* parent claim exists whose `job_id == parent_job_id`; the parent's `job_type` is `CARTO_MARKDOWN_GENERATE`; the child's `job_type` is `CARTO_REFRESH`; same `account_scope_id`; and the child's footprint is the parent's intended phase-8 target (same canonical path when both are path-keyed, else same graph `root_uuid`). "Overlapping but not the exact edge" (e.g. a folder parent and a contained-file child) does NOT confer co-claim or tombstone-bypass privilege. Only then does it co-claim and bypass the tombstone.
- Parent `finally` finalizes the parent's claim (token-verified) **without** writing a tombstone **only when the continuation is a validated, live, successfully-launched co-claim** — the child then owns the chain's cooldown.
- **Parent tombstone on failed child launch:** the parent checks the child launch's *result*. If the phase-8 admission is refused or fails (e.g. `footprint_unresolvable` on a stale cache, or spawn failure), **no live continuation exists**, so the parent's own finalize writes the tombstone itself. (The tombstone is skipped only when a child co-claim is genuinely holding the region.)
- Parent crash → liveness reaps the parent's claim (via `finalize_claim`); the child's persists.
- **Parent cancellation does NOT propagate to the child (F4, ruled):** cancelling the `CARTO_MARKDOWN_GENERATE` parent cancels the parent only. An already-launched, validated phase-8 `CARTO_REFRESH` continuation is independently owned and independently observable: it finishes, fails, or is cancelled under its OWN job_id and its OWN sentinel. Sentinels are job-scoped; no cross-job sentinel fan-out exists. The widget will show the child still active after a parent cancel — that is correct, not a leak.
- Third parties are refused throughout by *either* claim — zero unclaimed gap.
- `parent_job_id` is minted only inside the worker pipeline — **never** accepted on any MCP tool schema.

### 6.5 The one launch authority

`launch_carto_refresh_job(root_uuid, mode, extra_job_fields, launcher, parent_job_id=None, preparation=None)` lives in `carto_job_governance.py` and is the **only** code that spawns a CARTO_REFRESH worker. The optional `preparation` callback is the §8 claim-before-mutation seam: it runs outside `admission.mutex` while the admitted claim is launcher-owned, and only a successful preparation proceeds to spawn. **Dependency posture (F-6, explicit):** `carto_job_governance.py` is dependency-light like the governor — it must NOT import `server.py` or depend on MCP-process globals. The phase-8 caller runs **inside the detached MARKDOWN_GENERATE worker process** (not the MCP server), so the authority must be callable from `weave_worker` / `markdown_generate_pipeline` context. It receives credentials/environment, the jobs root, and launch metadata via **arguments** (or the caller's client object), never by reaching into server-side globals (e.g. the current server launcher reads `get_client()` / `get_nexus_runs_base_dir()`; those become injected arguments).

- **One independent reconcile ingress (v11, normative).** Every independently requested mutation-capable FILE/FOLDER disk→Workflowy reconciliation routes through this authority and therefore creates a CARTO job JSON + region claim before mutation. The synchronous `carto_async=false` branches are DELETED at all three live sites: FILE-node sync, FOLDER-node sync, and the AST-node default follow-on reconcile. For compatibility with an old extension or direct WS caller, the server normalizes a false/missing `carto_async` on every FILE/FOLDER/AST refresh action to the asynchronous launch (and logs that normalization); it never executes a synchronous fallback. Already in Phase 0, an AST beacon-write exception or result lacking explicit `success is True` produces an error response and ZERO follow-on refresh; Phase C strengthens this into the claimed prepared-launch predicate below. The only `dry_run=False` calls to `refresh_file_node_beacons` / `refresh_folder_cartographer_sync` that remain are the detached worker; explicitly named work nested inside an already-claimed `CARTO_BULK_APPLY` / `CARTO_MARKDOWN_GENERATE` owner; and the two primitive-internal edges (`refresh_file_node_beacons` routing a directory target to `refresh_folder_cartographer_sync`, and folder reconciliation invoking `refresh_file_node_beacons` per contained file). The directory reroute is covered by the admitted canonical directory path, whose prefix footprint protects the whole region even if the incoming mode was `file`. A static AST allow-list test locks this exact call graph.
- **Shared FILE/AST handler classification precedes freshness (v13, load-bearing).** `_handle_refresh_file_node` currently runs the fused preflight before deciding whether the target is a plain FILE or an AST/beacon node. Phase C MUST move FILE-vs-AST classification ahead of the freshness decision: a plain FILE performs forced freshness pre-admission; a prepared AST performs NO inline freshness, admits/schedules/acks immediately, then runs B.0 in the claimed background task. Deleting the top-level preflight wholesale would drop FILE freshness; leaving it in place would violate immediate AST acknowledgment. A missing compatibility `node_name`/`node_note` is resolved once at this boundary and frozen per §6.6 — never filled by a later mutable-cache read.
- **F12-on-AST is a prepared CARTO job, not a Q3 lease.** Both current popup choices (the sync "Fast node beacon update" and the "Async containing-file refresh") collapse onto ONE server flow: resolve the containing FILE path/graph footprint, admit the eventual `CARTO_REFRESH` claim in `preparing`, run `client.update_beacon_from_node(...)` as the preparation under that claim, then hand the SAME claim to the detached refresh worker. The direct disk write and the authoritative refresh are one observable job lifecycle with widget logging, cancellation, PID liveness, cooldown, and no lease→claim gap. The client may collapse the duplicate popup choices to one asynchronous action; server normalization remains the compatibility authority.
- **Low-level beacon writer is literally disk-only.** `WorkFlowyClientNexus.update_beacon_from_node` loses steps 4–6: no in-memory `/nodes-export` name patch, no cached-note metadata patch, and no synchronous auto-refresh. The `skip_auto_refresh` parameter is deleted from the method and every call site. This is load-bearing: steps 4–5 were historically suppressed in bulk mode because a helper's tag-stripped `base_name` patched mid-batch could make the later authoritative reconcile erase the user's newly typed tag. Every orchestrator explicitly decides whether a refresh follows; cache/Workflowy synchronization belongs to that claimed refresh, never to this disk primitive. `commit_beacon_write_plan`'s separate vestigial `skip_auto_refresh` parameter is also deleted (its body already never uses it; update the Q3 call site). The method itself never leases because it is a nested primitive used under either an owning CARTO claim or a Q3 lease established by the boundary.
- **Cache-name/note patch inventory is exactly four sites (v13).** Delete three: the low-level writer's tag-stripped cached-name patch (step 4), its cached-note patch (step 5), and `_handle_refresh_file_node`'s unclaimed pre-admission tag-bearing name patch. RETAIN the fourth: `_bulk_apply_per_file_inner_loop`'s tag-bearing `update_cached_node_name` call. That loop runs only as work nested under an owning `CARTO_BULK_APPLY` or `CARTO_MARKDOWN_GENERATE` claim and deliberately seeds the owning job's later per-file reconcile; it is sanctioned claimed cache work, not another ingress and not the writer's dangerous tag-stripped patch. A sweep finding four sites is expected; deleting the retained nested-owner site in the name of "disk-only" is incorrect.
- **Prepared launches acknowledge immediately; preparation is background work (v13).** Admission creates the claim + job JSON, schedules one in-process background task that owns freshness→preparation→spawn→finalize, and returns the normalized job acknowledgment to the WS/MCP caller immediately. The preparation callback does NOT run inline on the originating WebSocket pump: today `websocket_handler` awaits `_handle_refresh_file_node`, so inline preparation would block that same tab's polling and `carto_cancel_job` frames and make the promised cancellation during `preparing` unreachable. The background task runs in the launcher process, installs the job-scoped cancellation context, and owns every post-admission transition. It may be registered in the existing in-memory task registry for diagnostics, but the disk claim/job/sentinel remain authority. Scheduling, task-start, cancellation, or any other failure after admission — including `asyncio.CancelledError`/other `BaseException` exits that ordinary `except Exception` may miss — is post-claim and routes through universal finalize. This scheduling rule applies equally to F12+4/F12+5 and F12-on-AST prepared launches; it does not detach them into a subprocess. **The background task also owns uniform B.0 FRESHNESS, and the quiescence gate is gone:** its first action under the claim is the §8 B.0 /nodes-export freshness refresh, and it NEVER awaits CARTO-jobs quiescence (§4 doctrine — its own job JSON is active; awaiting global quiescence would deterministically deadlock on itself, the §7.1 bulk-apply class). The legacy inline `_handler_preflight_cache_quiescence` call is REMOVED from prepared ingress handlers — with it in place the ack is not immediate. This knowingly changes F12+4/F12+5's historical snapshot-patch-only fast path; the refresh is background and coalesced, and a bulk materialization must not induce N serialized refreshes. Plain FILE launches retain pre-admission FRESHNESS. Plain FOLDER launches now ADD the same forced pre-admission request+await (their live handler previously only awaited an already-running refresh). Both drop CARTO-global quiescence. F12+3 and standalone F12+2 likewise keep pre-admission freshness only.
- `server.py:_start_carto_refresh_job` (~9703) becomes a thin wrapper preserving its return contract for its remaining launch call sites.
- `markdown_generate_pipeline.py:_launch_post_refresh_subprocess` (~830/993) is **deleted**; the pipeline calls the authority.
- Bulk F12+4 leaves claim **real paths** (filenames are assigned collision-safely before launch), with graph chains.
- Temp regime (F12+5 / F12+4-temp, `source_path_override`): `path=None`, uuid-keyed claim, graph footprint only.
- **CARTO_BULK_APPLY (standalone F12+2) also takes a region claim** — its canonical FILE/FOLDER path plus the Workflowy root + ancestor chain (it already has both in hand at launch). The claim is acquired before its async runner begins and released in the runner's `finally`. Because it runs **inside the MCP process**: cancellation is cooperative only (§7.3); it is never force-killed; if the server dies, standard PID liveness reaps the claim later.
- **Every detached spawn uses the `spawning` handoff state + `spawn_grace` + mutexed claim adoption** (§8), not just prepared launches: a plain F12+1 / F12+3 / phase-8 / temp-regime launch is admitted directly in `handoff_state="spawning"`, records the child PID conditionally after `Popen`, and the worker adopts the claim under `admission.mutex` before any mutation-capable work. F12+4/F12+5 and F12-on-AST add the `preparing` state in front; the spawn race (launcher dies between `Popen` and the PID record) is common to ALL detached launches, so the seal must be too.
- **Nested work does not claim:** F12+3's internal bulk-apply phase is already covered by the owning MARKDOWN_GENERATE claim. Rule: *every independently running mutation job owns a region claim; work nested inside a claimed job does not mint another claim unless it becomes an independently surviving child process.*

### 6.6 Semantic dedupe key

> **v14 origin/freshness authority:** §18 is the closed caller matrix for this launch authority and the MARKDOWN_GENERATE/BULK_APPLY siblings. A new caller is not "covered by analogy": it must be added to the matrix and the structural caller-set test. Plain launch freshness is transport-neutral; prepared work uses claimed B.0; phase-8 is the explicit inherited-parent exception.

`dedupe_key = sha256(canonical_json([account_scope_id, job_type, mode, root_uuid, source_regime, source_path_override_norm, delete_temp_file_after, preparation_input_digest]))` per §3's canonical hash encoding. **The `mode` ingredient is polysemous — per-type value, fixed (R5):** for `CARTO_REFRESH`, `mode` ∈ {"file", "folder"}; for `CARTO_BULK_APPLY`, `mode` is the walk mode (visible/all); for `CARTO_MARKDOWN_GENERATE`, `mode` is absent → `""`. This is the **closed, complete ingredient list** — every field enumerated, each with its normalization: paths realpath+normcase; absent values → `""`; `delete_temp_file_after` normalized to `"true"`/`"false"`; **`source_regime` is an enumerated three-value string** — `"standard"` (an ordinary refresh / regenerate / bulk-apply of an already-mapped target), `"persistent_new"` (the F12+4 persistent-new-file regime: a real target path that did not exist as a mapped file at claim time), `"temp_override"` (F12+5 / F12+4-temp: `source_path_override` non-empty) — derived from the launch-intent fields, never free-form. Adding a field or a regime value is a rulings-level change, not an implementation choice. Two launches on the same footprint with different intents (F12+1 refresh vs F12+2 bulk apply vs F12+3 regenerate vs a temp-regime override refresh) are **overlap conflicts**, not dedupe hits. Only a byte-identical intent dedupes — and with `preparation_input_digest` below, "byte-identical" now includes the preparation payload bytes. This replaces the v3 "same target" language and the "always return the child" co-claim note.

**`preparation_input_digest` (v13 — closes the payload-dropping DedupeHit / deferred tag-erasure route).** For payload-bearing PREPARED launches (F12-on-AST, F12+4/F12+5), launch identity alone under-specifies the request: two F12s on the SAME AST node with DIFFERENT freshly typed name/note hash identically on the other seven ingredients, so the second (changed) request would be a DedupeHit whose payload is silently discarded behind a success-shaped ack — and the FIRST job's authoritative disk→Workflowy refresh could then ERASE the user's newly typed tag (Workflowy carries the tag, disk does not, reconcile is disk-authoritative): the exact outcome the §8 gate exists to prevent, reached through the admission front door with every gate passing. The digest makes a changed-payload re-fire a DIFFERENT intent → `overlap_conflict` REFUSAL with overwrite-honest teaching: "an active job owns this node; your latest name/note changes were NOT synchronized; the running disk-authoritative refresh may overwrite them in Workflowy — verify the node after terminal, then retry, or use F12+2 Bulk Apply on the containing FILE." Never silently drop the newer payload. **Normalization (per-type value, fixed — same doctrine as `mode`):** every NON-prepared launch type → `""` (so `CARTO_BULK_APPLY` is untouched and Ruling 76's dedupe-sameness acceptance stands unchanged); F12-on-AST → `sha256(canonical_json(["ast_beacon_write", node_uuid, fresh_name, fresh_note]))`; F12+4/F12+5 → `sha256(canonical_json(["materialize", node_uuid, note_body]))` plus any preparation-only option that changes the produced bytes and is not already a dedupe ingredient. **Compatibility fallback + binding invariant (load-bearing):** if an old frame omits `node_name`, `node_note`, or another hashed payload field, the boundary either fails closed or resolves the fallback ONCE from the admission-time snapshot, before hashing; that resolved value becomes part of the frozen payload. The preparation callback MUST consume the exact FROZEN snapshot the digest was computed from — never a later re-read after B.0 or from mutable cache/DOM state. The digest guarantees nothing unless the payload it hashed is the payload prepared. **Scope doctrine (do not expand — see §15):** this digest is SOLELY an active-job dedupe ingredient for payload-bearing prepared launches. It introduces NO content-addressed architecture and replaces NOTHING: not the Q3 exact-byte CAS, not parsed semantic node equality, not whitened-text comparison, not cache freshness, not payload transport. **DedupeHit ack teaching (prepared ingress):** a byte-identical prepared re-fire remains an ordinary DedupeHit, and its SUCCESS ack must state that an active job was reused and NO second preparation ran.

**CARTO_BULK_APPLY dedupe-sameness note (accepted, ruled):** the ingredient list deliberately does not capture walk-relevant input. Two same-root bulk applies launched at different times can therefore hash identically even though their effective work differs — most acutely for the `visible` walk mode, whose synthetic tree comes from the **client DOM payload** (NOT purely cache-derived: two visible-mode launches under different expansion states can hash identically while doing genuinely different work). The second is a DedupeHit and receives the active job, which is doing substantially the same sweep. Retry after the active job reaches terminal. Accepted behavior, not a hole — the acceptance stands even though the "cache-derived" rationale does not cover the visible-mode case.

### 6.7 Claim-aware GC and history clearing

All deletion or mutation of claims and live tombstones occurs **under the admission mutex**. Additionally:

- A job JSON referenced by a live claim is **never** deleted, regardless of displayed status or age.
- Manual "Clear job history" never deletes a live/unexpired tombstone (a UI cleanup gesture must not bypass cooldown).
- Dead-claim reaping re-reads and verifies `claim_id` under the mutex, and routes through `finalize_claim` (tombstone written).
- Tombstone expiry uses `last_terminal_at`, not an earlier unlocked snapshot.
- Sentinel and heartbeat cleanup occurs only when the job is terminal **and** no live claim remains.
- **Unclassifiable governance artifacts fail CLOSED everywhere.** An unparseable / schema-invalid claim or live tombstone is never skipped, auto-quarantined, or deleted: at admission it blocks with `governance_state_unclassifiable` (a claim whose overlap surface cannot be decoded may conflict with anything; a tombstone whose footprint/cooldown cannot be decoded cannot be cleared); the startup sweep, watcher reap, opportunistic GC, and manual history clearing likewise preserve it and surface it loudly. The recovery path is MANUAL: inspect the named artifact, repair or delete it deliberately. (Governor/breaker JSON is the explicit exception — §4's corrupt-state self-heal — because a pacing state's worst case is a few writes landing closer together, while a region claim's worst case is two mutators on one region.)
- **Orphaned sentinel/heartbeat reap:** a sentinel or heartbeat file whose job_id resolves to **no** job JSON **and** to **no** live claim is unclassifiable by deny-by-default and would otherwise be immortal (job_ids are UUIDs, never recycled). Such a file may be deleted once its age exceeds `admission.orphan_grace_seconds` (a multiple of `start_grace`; §12). No correctness hazard — the sentinel only ever matters while its job could exist — but this prevents unbounded accumulation.
- Applies to opportunistic `_gc_carto_jobs`, manual `_clear_carto_job_history`, the startup sweep, and the admission-time sweep.
- **The already-locked helper variants are MANDATORY, not optional (A-12):** `finalize_claim(...)` acquires `admission.mutex`; `finalize_claim_locked(...)` REQUIRES the caller to already hold it and never re-acquires. EVERY finalize/reap invoked from inside an already-held admission transaction calls the `_locked` form — including the ONE shared sweep's reaps **and the admission-transaction job-JSON-write-failure path in §6.3**. With non-blocking acquisition, calling the public acquiring wrapper from either site would busy-timeout and leak the claim. No new mutex.

### 6.8 Q3 disk-mutation leases — symmetric region ownership for `beacon.tags.ensure` / `tags.remove` / `sync_node` (F3, ruled)

**The gap closed.** The Q3 disk beacon mutations write source files atomically with a sha-CAS, but they mutate the SAME files a claimed CARTO refresh may explicitly repair/rewrite before reconciliation (including the §4 C0 repair step). Without symmetric ownership, one ordering is silently destructive: Q3 commits between a CARTO read/plan and a later source rewrite → stale CARTO bytes destroy the Q3 mutation with no error. A one-way read-only overlap check at Q3 commit time is INSUFFICIENT: it catches "CARTO active → Q3 starts" but not "Q3 active → CARTO starts" (CARTO admission would see nothing representing Q3). The fix is therefore SYMMETRIC: Q3 participates in region ownership via transient leases, and CARTO admission scans them.

**Lease lifecycle (mandatory order — zero mutations before leases exist):**

1. Resolve and preflight ALL target files and graph footprints with zero mutations (the existing Q3 Phase-B/Phase-C preflight output is the input).
2. Under `admission.mutex`, in ONE all-or-nothing transaction:
   - run the shared §6.3 sweep machinery over claims AND `.q3_leases/` (the sweep covers both — see §7.1's one-sweep mandate); the §6.3 A-11 claimless-job gate runs here too — a LIVE/unknown claimless CARTO job JSON globally blocks Q3 acquisition exactly as it blocks admission;
   - apply the §6.2 overlap predicate of every actionable target against every active CARTO claim and every other active Q3 lease. Live TOMBSTONES are NOT consulted by Q3: cooldown governs CARTO relaunches only, and a Q3 edit is not a mutation the cooldown exists to defer (Q3 → F12+1 is the expected immediate sequence).
   - any overlap → refuse the whole operation with `overlap_conflict` naming the conflicting job_id/lease_id and path, before ANY disk write;
   - otherwise create one lease file per actionable target under `.q3_leases/`;
   - **partial-create rollback (v13):** these are N file writes inside one logical all-or-nothing transaction. If any lease write fails, delete every lease successfully created by THIS acquisition while still holding `admission.mutex`, perform ZERO disk mutations, and fail loudly. If rollback deletion itself fails, preserve/name the residual lease as a safe blocking artifact for manual recovery — never pretend acquisition succeeded and never delete another operation's lease.
3. Perform the JIT re-plan/CAS commits OUTSIDE the mutex while the leases remain live.
4. Release every lease in `finally` (delete under `admission.mutex`). An
   admission-lock acquisition failure or residual exact-token unlink failure is
   a loud `governance_cleanup_required` outcome, not clean mutation success.
   The live MCP owner registers the exact lease obligation and keeps one
   automatic async-backoff supervisor for it until release or proof that the
   exact token is already absent. A replacement lease with a different
   `lease_id` is preserved and is never targeted by path alone. Cancellation
   preserves/queues the obligation and re-raises; no transaction begins after a
   cancelled lock wait. Q3 cleanup still writes NO tombstone. While a named
   lease remains blocking, stop mutation-capable work on that affected region;
   unrelated regions may continue. Never age-delete a live-owner lease.

**Lease file content:** same identity discipline as claims — `lease_id` (uuid4 hex), full footprint (path + root_uuid + ancestor_chain + kind), `account_scope_id`, `pid` + `pid_create_time` (provenance) + the additive-optional `pid_start_ticks` + `pid_boot_id` stable-identity pair (U01) of the owning (in-process MCP) process, `created_at`. Writes use the §4 atomic-replace primitive (R3).

**CARTO admission change:** the §6.3 overlap scan reads `.q3_leases/` in addition to `.refresh_locks/`; a live Q3 lease overlapping a launch footprint refuses the launch with `overlap_conflict` (naming the lease). The dedupe and cooldown rules do NOT apply to Q3 leases (a lease is not a job intent; a lease mints no tombstone).

**Reaping:** a lease whose owner PID is verified dead is reaped under `admission.mutex` by the shared sweep — **by plain lease deletion, NOT `finalize_claim`, and NO tombstone is written.** Rationale: Q3's atomic/CAS disk writes complete before lease release, so once the operation is over (or its owner died), immediate CARTO reconciliation is not merely safe but the EXPECTED next step (Q3 → F12+1 is the normal workflow); a 60 s cooldown after Q3 would obstruct it. Cooldown tombstones exist to defer CARTO relaunches after CARTO mutation bursts, not after Q3 edits.

**Deny-by-default applies to leases identically:** unparseable/schema-invalid lease → `governance_state_unclassifiable` (blocks both Q3 acquisition and CARTO admission; manual recovery); unknown owner liveness ⇒ lease treated as live ⇒ blocks overlap; never auto-deleted except via the verified-dead-owner reap.

**Safety matrix (the property this buys):**

| Launch order | Result |
|---|---|
| CARTO active → Q3 starts | Q3 refuses (`overlap_conflict`) |
| Q3 active → CARTO starts | CARTO refuses (`overlap_conflict`) |
| Two overlapping Q3 operations | second refuses |
| Non-overlapping operations | both proceed |

**Standalone single-target writer (A-13, narrowed in v10).** The legacy-profile direct `update_beacon_from_node` MCP wrapper remains registered because wholesale removal of the legacy 37-tool surface is a separate non-goal, but its behavior is corrected to match its own disk-only description: it acquires ONE single-target Q3 lease for the resolved file before the first disk write, calls the now-disk-only low-level writer, and releases the lease in `finally`; it performs NO synchronous auto-refresh and returns no fabricated visual-sync success. The WS F12-on-AST path is **not** a Q3 lease ingress anymore — §6.5/§8 make its direct disk write preparation under the eventual CARTO claim, eliminating the lease→claim gap and self-conflict. `beacon.sync_node` remains part of the main Q3 lease lifecycle above. The low-level client method never leases BY CONSTRUCTION: nested calls inside claimed BULK_APPLY/MARKDOWN_GENERATE/prepared-refresh work would collide with their own owner. The dead `_maybe_create_ast_beacon_from_tags` helper (no call sites in the current source) receives NO governance — remove it during nearby cleanup rather than governing dead code.

**Scope boundary (honest):** this prevents CONCURRENT overlap among system-managed mutation surfaces. It does not govern ordinary external `edit_file` writes, manual editor changes, or browser-side human edits; it refuses rather than queues; and it does not make a stale cache current (callers still wait for terminal jobs / required refreshes).

## 7. Component: Worker lifecycle control

### 7.1 Liveness truth layer

- **ONE shared sweep implementation, three call sites (mandated).** The admission-time sweep (§6.3), the watcher-loop persistence sweep, and the §7.5 startup sweep are THREE TRIGGERS of ONE function (e.g. `sweep_region_governance_locked(...)`, in `carto_job_governance.py`), never three hand-written sweeps. That single implementation owns: unclassifiable-artifact fail-closed handling, claim AND Q3-lease liveness classification, spawn-grace handling, terminal-status preservation, cancelled-vs-vanished selection, `finalize_claim` routing (claims) vs tombstone-less deletion (Q3 leases), and loud diagnostics. The spec's semantic parity across the three paths is guaranteed by construction, not by keeping three codebases in sync.
- **Claimless non-terminal job JSONs — the legacy/fallback rule (F1, closes the permanent quiescence-wedge).** The claim file is the single liveness authority WHEN A CLAIM EXISTS. A non-terminal job JSON with **no claim for its `job_id`** is instead liveness-checked against the job JSON's OWN `pid` (the only identity available), with explicitly degraded semantics: legacy JSONs carry no `pid_create_time`, so ONLY PID-nonexistence counts as death evidence (a recycled live PID conservatively presents as alive — bounded to legacy artifacts); dead PID — or pidless with the job older than `start_grace` — ⇒ persist `failed` (`"worker process vanished (pid N); no governance claim"`), or `cancelled` when a sentinel exists, **with NO tombstone** (no claim ⇒ no region ⇒ no cooldown to write). Unknown/unverifiable ⇒ alive ⇒ untouched (deny-by-default preserved). This fallback runs ONLY when no claim exists; the claim remains the sole authority whenever one does. **Migration note:** the FIRST startup sweep after rollout is EXPECTED to terminal-ize every stale pre-governance job JSON via this fallback — today's code has no PID liveness for detached `CARTO_REFRESH` at all, so crash residue from the pre-governance era (including the incident era) permanently presents as `running` and wedges `_await_carto_jobs_quiescent` forever; that wedge class is exactly what this rule retires. (Three real claimless sources: pre-governance rollout residue; a reap whose best-effort status write failed (R2); any future path where a job JSON outlives its claim non-terminally.) This same classification also GATES admission and Q3 acquisition — §6.3's A-11 claimless-job gate: ALIVE/UNKNOWN claimless jobs are a global transient conflict; DEAD ones are terminal-ized and never block.
- **Presented-status vocabulary is closed (R9).** The scanner's view-layer classification presents dead-PID jobs as `failed` — there is NO `orphaned` status string anywhere in the system. The tracker/GC deny-by-default treats any unrecognized status as ACTIVE (immortal), so no new presentation vocabulary may leak into persistence without a rulings-level change.
- `_scan_carto_job_files` gains **view-level** liveness classification for all `CARTO_*` job types via psutil (PID existence + creation time), reading owner identity from the job's CLAIM file (the §3 authority), never from the job JSON's `pid` mirror — falling back to the claimless-job rule above only when no claim exists. Non-terminal status + recorded PID dead ⇒ presented as failed in the returned view. The scanner stays **read-oriented** — persistence happens in the `_carto_jobs_watcher_loop` and the startup sweep.
- **`CARTO_BULK_APPLY` retires its existing `pid != os.getpid()` in-process heuristic** (`server.py:1015`). That heuristic falsely marks server B's legitimately running bulk apply as orphaned when scanned from server A (the normal multi-server topology). BULK_APPLY joins the standard psutil PID-identity classification like every other CARTO type. (PID identity suffices for *liveness*; command-line `--carto-job-file` identity is required only before *force-killing* a detached worker.)
- Persistence path writes `status="failed"` with `"worker process vanished (pid N)"` via `merge_write_carto_job_status` (sticky terminal). **Exception:** a dead process carrying a cancellation sentinel is persisted as `cancelled`, not "failed/vanished".
- Grace windows: `start_grace` (30 s) is a **presentation/diagnostic** window only — a claim younger than `start_grace` whose job JSON is missing or pidless is *presented* as starting and exempt from "job record missing" diagnostics; it NEVER authorizes a reap (owner-PID liveness on the claim is the only death authority, §6.3). A claim whose `handoff_state` is **`spawning`** is granted `spawn_grace` (§8, §12) before any reap.
- Unknown liveness ⇒ alive ⇒ never reaped, never killed.
- **Tracker vocabulary:** `_refresh_carto_job_tracker_once`'s hardcoded `active={"queued","running"}` / `terminal={"completed","failed","cancelled"}` sets are replaced by the shared `is_carto_job_active` / `is_carto_job_terminal` authorities. `cancelling`, `waiting`, **`preparing`, and `spawning`** classify as active; `completed_with_warnings` classifies as terminal and **does** trigger the terminal cache refresh (fixes a live bug: warned jobs never refresh the cache). Deny-by-default: any future/unrecognized status is non-terminal ⇒ active.
- **`cancelling` presentation overlay lives in the scanner.** Because the widget reads `_scan_carto_job_files`, the scanner itself applies the sentinel overlay (see §7.2): whenever a cancellation sentinel exists for a job whose persisted status is non-terminal **and** whose claim is live, the scan presents the job as `cancelling`. This is the invariant — it does not depend on winning a write race (§7.2's corrective write is hardening, not the guarantee).
- **Bulk apply's inner CARTO quiescence wait is removed — ONLY the `_await_carto_jobs_quiescent(...)` call.** The runner's opening sequence is THREE awaits: `_await_nodes_export_cache_quiescent` → `_await_carto_jobs_quiescent` → `_await_nodes_export_cache_quiescent`. Only the MIDDLE one self-deadlocks once `waiting` correctly classifies as active; the two cache-quiescence waits are status-vocabulary-independent (they gate on the /nodes-export refresh worker, not on job status) and MUST stay. Its sole caller (`server.py:8579`) already runs `_handler_preflight_cache_quiescence` before starting the job. **(R10 — verify, don't trust:** before deleting the inner wait, confirm at implementation time that the preflight genuinely precedes the start on every path into `_start_carto_bulk_visible_apply_job`; the sole-caller fact is verified, the ordering is asserted here from code reading, not execution.) (v13: that preflight is SPLIT per §4 — its CARTO-global quiescence gate is retired; standalone F12+2 retains only the forced FRESHNESS request+await before starting its claimed job.)

### 7.2 Cancellation sentinels (authority) + `cancelling` (presentation)

- `system.job.cancel` and the WS `carto_cancel_job` handler: (1) atomically create `.cancel_requests/<job_id>.cancel` — the cancellation **authority**; (2) write `status="cancelling"` via merge_write for presentation (non-terminal, sticky against stale progress writes).
- **Cancel dispatch order — sentinel first, always.** For any job that owns a **claim** (all CARTO_* types, including the in-memory-registered `CARTO_BULK_APPLY`), the cancel path is *authority then presentation then mechanism*: create the sentinel (authority), write `cancelling` (presentation), *then* deliver the in-process mechanism. Today `_system_job_cancel_impl` checks the in-memory `_jobs` registry first and fires raw `task.cancel()` **without** creating the sentinel or `cancelling` — a sentinel-free side door. v5 closes it: a claimed job's cancel must establish the sentinel before any task cancellation. Whether `task.cancel()` is retained as the in-process delivery vehicle (after the sentinel exists) is an implementation choice — it is well-behaved (`CancelledError` at await points, `finally`-block finalize) and may be kept, but only *after* the sentinel and `cancelling` exist so the authority/presentation invariants hold.
- **The two detached direct-terminal side doors are retired explicitly (v13).** Today `_system_job_cancel_impl`'s detached-CARTO fallback and the WS `carto_cancel_job` handler write `status="cancelled"` directly with no sentinel. Both migrate to the same authority→presentation→mechanism sequence above: create sentinel, persist `cancelling`, then poll/escalate. A request handler never writes terminal `cancelled` as its first action; terminal `cancelled` belongs only to token-verified worker/controller finalization after mutation stop is confirmed.
- **All six cancellation checker sites** migrate to sentinel-first: `_carto_should_cancel`, `_carto_should_cancel_file`, `_carto_job_cancel_requested` (server.py), `_job_cancelled` (markdown_generate_pipeline.py), the `reconcile_tree` cancel callback, and the CRUD-sleep polling. **Plus the two worker startup early-exit checks (F-5, R13):** `weave_worker.main()` currently contains startup guards `if job.get('status') == 'cancelled': exit` in **both** the `carto_refresh` and `markdown_generate` branches; under v7+ semantics a pre-start cancel writes `cancelling` (non-terminal) + a sentinel, so a literal `'cancelled'` string check will no longer fire. These startup checks migrate to sentinel-first as well (sentinel present, OR transitional status `cancelling`/`cancelled`), so a cancel issued during `spawning` still prevents a just-adopted worker from doing bootstrap work. **Ownership distinction is normative:** an exit BEFORE successful claim adoption never finalizes a claim it does not own; an exit AFTER adoption token-verifies the sentinel, persists terminal `cancelled`, calls `finalize_claim`, and only then exits. A post-adoption startup cancel is therefore a normal one-exit-door completion, never a bare process exit that waits for a later vanished-worker reap. Transitional status checks accept `cancelling` OR `cancelled`; sentinel existence is the lasting authority. Poll cadence unchanged (≤ ~1.25 s worst-case inside a single large file's apply phase; optionally drop the F12 caller's `cancel_check_interval` from 10 → 1).
- **Merge precedence for job status** (extends `merge_write_carto_job_status`):

  ```
  on-disk cancelled | failed                → always preserved (sticky terminal)
  on-disk completed_with_warnings           → preserved over completed and any
                                              non-terminal write; yields only to
                                              cancelled | failed
  on-disk completed                         → preserved over non-terminal writes;
                                              yields to cancelled | failed |
                                              completed_with_warnings
  on-disk cancelling                        → preserved over non-terminal writes;
                                              yields to ANY terminal write
  otherwise                                 → accept incoming
  ```

  **Behavior change, explicit:** the legacy `failed → cancelled` merge transition is RETIRED. The v5/v6 cancel semantics make it unreachable and undesirable: a cancel against an already-terminal job answers `already_terminal` and writes nothing (§7.3), and a live job's cancelled-vs-failed outcome is decided by sentinel presence at persist time (§7.1). A failed job is therefore never overwritten to cancelled. An implementer extending `merge_write_carto_job_status` must REMOVE the legacy transition, not preserve it.

- **Sentinel-sealed status merge (closes the cancel-vs-progress TOCTOU).** `merge_write_carto_job_status` does re-read → merge → `os.replace`, which is *not* a serialized transaction: a worker that read `running` just before the cancel write can `os.replace` over the `cancelling`, regressing presentation. The fix is layered, and **status is presentation-only (principle 8), so the guarantee must not depend on winning the write race**:
  1. *Invariant (the guarantee):* the **scanner overlay** (§7.1) — sentinel present + live claim + non-terminal persisted status ⇒ presented as `cancelling`. This holds regardless of any write race.
  2. *Hardening (best-effort, not the guarantee):* the status writer (a) inspects the sentinel before writing a non-terminal status and, if present, forces the written status to `cancelling`; (b) after the atomic replace, rechecks the sentinel and performs one bounded corrective write if a sentinel appeared between the first check and the replace. This narrows the window but is explicitly *not* relied on for correctness.
  3. Terminal outcomes still follow the precedence table: if mutation work genuinely completed before the cancel became effective, a true terminal completion may win; claim/PID remains stop truth.
- **Token-verified cancel finalization (and its ORDER):** a worker that observed the sentinel and stopped mutation work re-reads the sentinel file before writing `status="cancelled"`; if the sentinel is gone it must not finalize as cancelled (keeps "sentinel = authority" airtight). If the sentinel is gone, the worker finalizes as `failed` with a loud explanatory message ("cancellation sentinel vanished before finalization") — practically unreachable, since GC never removes a live-claim sentinel, but the outcome is specified so no implementer guesses. **The persisted terminal status write happens BEFORE `finalize_claim` (claim release)** — the same order §7.4 mandates for normal finalize and R2 mandates for reaps; the §16.2 diagram shows this order. Releasing first would drop the scanner's `cancelling` overlay (no live claim) and briefly re-present the job as plain `running`.

### 7.3 Escalation to exact-PID force kill

After the sentinel + `cancelling` write: poll ≤ 5 s for **claim release or verified PID death** (NOT job status — the handler just wrote a status itself; status is presentation, never stop authority). Still alive → verify exact PID identity with psutil: creation time matches **and** `--carto-job-file <this job file>` appears in the process command line (protects against PID recycling onto a *different* weave_worker) → `psutil.Process.terminate()` → wait ≤ 2 s → `psutil.Process.kill()` if still alive.

- **Re-read CURRENT ownership before the kill/refusal decision (A-14).** The controller must not cache the PID or `execution_owner` observed when the cancel began: `spawning` can transition launcher → detached_worker DURING the cooperative poll (the C.3 record or worker adoption lands mid-poll). After the poll, re-read and claim-token-verify the target claim under `admission.mutex`; if the claim is gone the outcome is `cooperative`; if ownership changed, the CURRENT owner decides (`detached_worker` ⇒ exact-PID escalation proceeds against the child PID; `launcher` ⇒ `kill_refused_in_process_job`). The mutex is released BEFORE any terminate/wait/kill operation (§2's ms-hold rule). Locked by a test: cancel begins during `spawning` with launcher ownership, the C.3 record/adoption lands mid-poll, and the controller escalates against the child identity — never the cached launcher identity.
- **RETIRED (U01) — the epsilon creation-time comparison is gone.** `pid_create_time` was once compared within a documented 1 ms epsilon; on Linux that epoch derives from `/proc/stat btime`, which steps under clock adjustment, so a live owner could be classified dead and reaped. Kill verification now compares the claim's stable-identity fields EXACTLY (`pid_start_ticks`, plus `pid_boot_id` when the claim carries one); a legacy claim (no stable fields) verifies on PID existence alone. The `--carto-job-file` cmdline match is exact-string.
- **No `taskkill`.** `psutil.terminate()` is exact-process on Windows (and TERM→KILL on POSIX); "never `/T`" is true by construction. The F12+3 phase-8 child is structurally spared.
- **In-process jobs are never killed.** The kill-refusal decision keys off **`execution_owner`** (A-3), not the handoff-state word: any job whose `execution_owner` is `launcher` runs inside the MCP server process — a `CARTO_BULK_APPLY`, or an F12+4 job still in `preparing`, or one in `spawning` **before** the C.3 post-`Popen` record (§8) — and reports `kill_refused_in_process_job` rather than being terminated; the PID may be perfectly verified, but killing it would kill the whole MCP server. A job whose `execution_owner` is `detached_worker` (after C.3, or after adoption sets `running`) is a genuine child process and MAY be force-killed after exact-PID verification.
- Identity indeterminate ⇒ **do not kill** ⇒ `kill_refused_unverified_pid`.
- Outcomes vocabulary: `cooperative | forced | already_terminal | kill_refused_unverified_pid | kill_refused_in_process_job`.
- **Accepted common case (documented, not hidden):** workers poll cancellation every 250 ms *inside sleeps*, but a worker mid-HTTP-call (httpx timeouts 30 s+) cannot observe the sentinel until the call returns. The ≤5 s poll therefore frequently force-kills a healthy worker during a network stall — "cooperative" rarely wins precisely when cancels happen. This is **safe by construction**: the kill is exact-PID, and the universal finalize/tombstone path is idempotent (a killed worker's claim is reaped via `finalize_claim`, tombstone written), so no corruption or claim-leak is possible. It is documented here so a forced kill mid-HTTP is understood as the accepted common case, not a defect.
- Both existing worker launchers already pass `--carto-job-file` on argv (verified: `server.py:9861/10039`, `markdown_generate_pipeline.py:1017`).

### 7.4 Release ordering — `finalize_claim`, the one exit door

- Normal finalize: finish all mutation-capable work → persist final progress/status → **finalize_claim** → exit.
- `finalize_claim(claim_id)` is ONE atomic transaction under the admission mutex. **Two layers (A-12, mandatory):** the public wrapper ACQUIRES the mutex; `finalize_claim_locked(claim_id)` requires the caller to ALREADY hold it and never re-acquires. Every call site chooses by lock ownership, not by semantic label: shared-sweep/watcher/startup reaps and the §6.3 admission-transaction job-JSON failure use the `_locked` form; normal worker/preparation/cancellation exits use the acquiring wrapper. Both run the identical body:
  1. re-read and verify `claim_id`;
  2. max-merge/write the tombstone;
  3. delete the claim.
  **Failure semantics (explicit):** the locked authority classifies each attempt as
  `released`, `already_absent`, `token_mismatch_or_ambiguous`, or `blocked`.
  `already_absent` is successful idempotence: no obligation is created and no
  extra tombstone is written. `token_mismatch_or_ambiguous` is a loud safe
  no-op: it never touches another claim or tombstone and never schedules a
  path-only retry that could target a replacement owner. `blocked` means the
  exact claim still exists but tombstone publication, re-read, or unlink could
  not complete. If tombstone publication fails, claim deletion MUST NOT run:
  the claim stays active and keeps blocking overlap until the tombstone can be
  written (fail-closed — a missing tombstone silently erases cooldown; a
  lingering claim only conservatively blocks).
  **Live-owner cleanup recovery:** a non-cancellation failure while acquiring
  `admission.mutex`, or a residual `blocked` result after bounded immediate
  retries, registers the exact claim cleanup obligation before returning a
  loud `governance_cleanup_required` failure. The owning MCP process maintains
  exactly one automatic supervisor per obligation key and retries through the
  same token-safe locked authority with bounded asynchronous backoff until the
  claim is released, proven already absent, or the process terminates. Caller
  cancellation never starts a post-cancel transaction: it preserves/queues the
  exact obligation and re-raises cancellation; the supervisor may retry later.
  A terminal job status is presentation and does NOT prove ownership release.
  While cleanup remains unresolved, stop mutation-capable work on that affected
  region, inspect the named artifact, and do not repeatedly re-fire; unrelated
  regions may continue. If live-owner recovery does not complete, restarting
  the owning MCP process permits the ordinary verified-dead-owner startup sweep
  to recover it. Never age-delete a live-owner claim.
  (Parent side of a validated live continuation: deletes its claim, writes **no** tombstone — the child owns the chain's cooldown; see §6.4's failed-launch rule.)
- **Universal finalization:** once admission has created a claim, EVERY terminal exit — success, worker failure, cancellation, preparation failure, job-file failure after claim creation, spawn failure, **or a reaped dead-owner claim** — goes through `finalize_claim` and creates/max-merges the cooldown tombstone. This may impose a 60 s cooldown after a spawn failure that mutated nothing; that conservative delay is accepted in exchange for deleting the `mutation_started` rollback state machine. One rule: **admitted claim + terminal exit ⇒ terminal status + atomic tombstone-and-release.** A reaped dead-PID claim is a terminal exit and routes through the same door (tombstone written) — never a bare claim delete.
- Cancellation: the claim is **not** released when the cancel is requested — only after the worker confirms stop (token-verified finalize) or PID death is verified post-kill (liveness reap via `finalize_claim`). A new overlapping launch can never start while a cancelled worker is still winding down.

### 7.5 Startup sweep (`lifespan`)

On MCP server start: run the ONE shared sweep implementation (§7.1) against the jobs dir: liveness-check every claimed job and every CLAIMLESS non-terminal job JSON (the §7.1 legacy/fallback rule — the first post-rollout sweep is the migration point that terminal-izes all pre-governance crash residue); dead ⇒ persist failed ("worker process vanished") — or `cancelled` when a sentinel is present — **and reap its claim via `finalize_claim`** under the admission mutex (tombstone written, not a bare delete; claimless jobs get the status write only, no tombstone). **Never kill live workers** — a live orphaned worker is legitimately finishing and releases its own claim on finalize. Force-kill only ever happens via explicit cancel (§7.3).

## 8. Component: Pre-spawn preparation seams (F12+4/F12+5 + F12-on-AST) with launcher→worker handoff

Two existing flows mutate before their eventual detached refresh would own the region:

1. **Single/bulk F12+4 and F12+5** write a generated `.md`, rewrite the node note, and sometimes patch the nodes-export snapshot before launching F12+1.
2. **F12 on an AST/beacon node** writes/updates/deletes the source beacon from fresh Workflowy name/note state, then refreshes the containing FILE. The current popup exposes both a synchronous "Fast node beacon update" and an async variant; the synchronous branch runs a full unclaimed reconcile, while the async branch still performs the disk mutation before its claim exists.

Required: each flow acquires the **eventual CARTO_REFRESH claim before its first disk or Workflowy mutation**, runs its bounded preparation under that active claim, and carries the same claim into the spawned worker with no release/reacquire gap. The AST path is therefore NOT a Q3 lease followed by a claim. **Preparation must NOT hold `admission.mutex`** (per §2's millisecond-hold invariant): it may wait on the write governor, perform an HTTP write, write a source/Markdown file, and parse/replace the large nodes-export snapshot — unbounded work that must never sit inside the machine-wide mutex. The design below runs preparation **under an active claim, outside the mutex**, with an explicit launcher→worker ownership handoff.

### The handoff states (new tracker vocabulary; both classify as ACTIVE)

| State | `execution_owner` | Meaning |
|---|---|---|
| `preparing` | launcher | claim + job JSON created; launcher is preparing (disk/Workflowy mutations) outside the mutex |
| `spawning` (before C.3 child-PID record) | launcher | prep done; launcher is about to spawn (or has just spawned but not yet recorded) the detached worker |
| `spawning` (after C.3 child-PID record) | detached_worker | child PID recorded on the claim; worker has not yet adopted |
| `running` | detached_worker | detached worker has adopted the claim under the mutex and owns it |

**The kill-refusal / cancellation decision keys off `execution_owner`, not the handoff-state word (A-3):** `execution_owner=launcher` ⇒ in-process ⇒ never force-killed (§7.3 `kill_refused_in_process_job`); `execution_owner=detached_worker` ⇒ genuine child process ⇒ may be force-killed after exact-PID verification. The word `spawning` alone does NOT imply in-process: after C.3 the state is still `spawning` but the owner is already the child.

`execution_owner` records who owns the PID in the CLAIM (mirrored to the job JSON): `launcher` (during `preparing`, and during `spawning` until the C.3 record) or `detached_worker` (after the C.3 post-`Popen` record, and unconditionally after mutexed claim adoption). `preparing` and `spawning` are added to the tracker vocabulary (§7.1) and to `is_carto_job_active`.

### The state sequence

```
A. ADMISSION (under admission.mutex; ms hold)
   sweep → dedupe/overlap/cooldown → create claim + initial job JSON in ONE

   prepared launches (F12+4/F12+5 + F12-on-AST):
             handoff_state/status="preparing", execution_owner="launcher",

             claim_id, dedupe_key, footprint, account_scope_id, launcher,
             parent_job_id

             admitted directly with handoff_state="spawning" + spawn_started_at

     finalized by the admitting coroutine. Plain launches proceed directly to C.

       running N serialized refreshes. It NEVER awaits CARTO-jobs quiescence —

     - F12-on-AST: perform the now-disk-only update_beacon_from_node against

   - SUCCESS GATE (v11 predicate, v13 presentation split — normative and tied

     "created_beacon", "deleted_beacon"}`. Those are the only three named

     disk→Workflowy refresh (which could erase the user's newly typed tag).

       * FIRST, `result.get("reason") == "virtual_group_noop"` (its live shape

      merge-write is not part of that same ordering guarantee from the

      `running` presentation. Identity-only mirror ⇒ no status regression.

      self-registration at weave_worker.py:443/937). **Adoption ordering
      (F-3, R11 — pin, do NOT replace the old self-registration site in
      place):** the worker adopts the claim BEFORE constructing its client
      and BEFORE any cache bootstrap. `weave_worker.main()` today reaches
      the self-registration site only AFTER argparse → sys.path setup →
      `WorkFlowyClient` init → and (in the no-warm-start branch) a full
      `/nodes-export` cache refresh — a ~30k-node download that can exceed

      job JSON → the R7 `.<job_id>.lock.json` suffix scan → `os_lock`), so
      `spawn_grace` budgets process start + interpreter/import time only,
      never API/cache latency. A worker that adopts late (after bootstrap)
      risks a spurious false-failed reap under load; a worker that adopts
      first and THEN discovers a sentinel (F-5 startup check) performs the

      status, then `finalize_claim`, then exit — before any expensive bootstrap.

            JSON → claim_id)

      adopts first (the sweep then sees a live owner PID) or the reap wins
      (the worker finds no claim and dies). No spawn_grace value can leak a
      zombie mutator.

claim by scanning `.refresh_locks/` for the filename suffix `.<job_id>.lock.json`

D. DURING "spawning", the sweep grants spawn_grace (§12) before any reap

     before recording the child PID, the live worker re-asserts its own PID

     finalize_claim (the owner PID — the launcher's — is dead). A worker that
```

- On preparation failure: universal finalize (§7.4) — terminal status + tombstone + release; no worker spawn.
- **Cancellation during `preparing`/`spawning`:** the decision keys off `execution_owner` (A-3). A job whose `execution_owner` is `launcher` (an F12+4/F12+5 or F12-on-AST job in `preparing`, or in `spawning` before the C.3 record) runs in-process, so §7.3's escalation **never kills the MCP server** — it returns `kill_refused_in_process_job` if cooperative cancellation does not finish in time. Cooperative cancellation still applies (job-scoped context, §4), so a cancelled preparation stops waiting promptly. - Preparation Workflowy writes ride the governor like everything else; preparation disk writes ride the active CARTO claim. Both use **job-scoped** cancellation context (§4).

After terminal, the ordinary 60 s tombstone may refuse `cooldown_active`. ## 11. Error vocabulary (new)

- `AccountWriteBlockedError` (models/errors.py; non-retryable, not a NetworkError subclass; `retry_after`, `blocked_until`, `reason`). Never caught or re-wrapped by CRUD retry loops.
- `WriteGovernorUnavailableError` (names the inaccessible governance path; the *broken* branch).
- `WriteGovernorDeferredError` (governor healthy, but the computed write slot lies beyond `max_wait_before_refusal_seconds`; non-retryable by CRUD loops; carries non-negative `retry_after`, `deferred_until`, and reason; ZERO ticket/state advance and ZERO HTTP call). Distinct from WFB `AccountWriteBlockedError`, mutex busy-timeout, and path failure.
- `AdmissionUnavailableError` (names the inaccessible admission path; the *broken* branch).
- `*BusyTimeout` refusal kinds (the *busy-past-window* branch): distinct from the broken errors above; still fail-closed (no write / no admission), reported as busy-timeout, never as broken.
- Admission refusal kinds (structured results, not exceptions, at the launcher): `overlap_conflict` (conflicting job_id + path), `cooldown_active` (`retry_after`), `footprint_unresolvable` (teaching: run `system.cache.refresh`), `governance_state_unclassifiable` (names the exact malformed claim/tombstone artifact path; manual inspection/removal is the recovery path). On an individual-node F12 refusal caused by same-file overlap/cooldown, the teaching text additionally recommends **F12+2 Bulk Apply on the containing FILE** for multi-node synchronization; this is a context-specific message field, not a new refusal kind.
- Cancel outcomes: `cooperative | forced | already_terminal | kill_refused_unverified_pid | kill_refused_in_process_job`.

## 15. Non-goals (v1 — do not "fix" these later without Dan)

- Durable cross-process job **queue** (refusal + `retry_after` suffices; a queue is a subsystem).
- Process-count cap K (the governor subsumes it).
- Reorder-storm minimal-move algorithm (the structural blast-radius reduction; separate project).
- Read-path pacing *by the governor* (reads are ungoverned; the existing per-process read-delay sleeps are kept, but the governor/breaker never touch reads).
- Legacy MCP tool-surface removal (separate task).
- Browser-side human mutations (F10 marker toggle, manual GUI edits — human tempo, not agent-amplified; by construction outside the governor).
- Per-tool warnings beyond `map.refresh` (the governor makes them unnecessary).
- Region claims for ordinary single-node edits (tag/edit/anchor captures) — they pass through the write governor, which suffices at that write volume.
- 429 reservation recall, ticket generations, or any re-queue machinery (bounded leakage accepted).
- Downward-clamping a *valid* `Retry-After` (valid server values are persisted account-wide exactly; §5.3 may refuse an individual caller rather than making it sleep beyond 30 s, which is not a clamp; the manual state-file delete is the override).
- Converting `CARTO_BULK_APPLY` into a detached worker mode (standard psutil liveness + job-scoped cooperative cancel is the smaller correct change).
- Converting bounded preparation/Q3 operations into separate detached jobs. F12+4/F12+5 and F12-on-AST preparation stay in the launcher process **under the eventual CARTO claim**; Q3/beacon.sync_node stay synchronous under transient leases. Detaching these short transactions would add lifecycle machinery with no safety gain.
- Cross-runtime-directory or cross-machine coordination.
- Pre-claim bulk-F12+4 cross-process filename assignment (names are chosen before claims exist; the losing process's admission dedupe/refusal lands before any mutation, so the residual is partial-bulk UX, never concurrent writers on one file).
- API-key-rotation domain bridging (rotating the key mid-flight mints a new `account_scope_id` → two independent pacers against one account until old processes drain; accepted, documented, not engineered around).
- **Rolling-deploy mixed-version fleets (F6, accepted).** Multiple MCP hosts restart at different times (the uv cache-clear flow); during the window, an old-code process bypasses governor, breaker, and admission entirely and silently — there is deliberately NO version handshake in the shared state. The documented all-hosts-shutdown deploy discipline is the mitigation; partial-fleet behavior is accepted, not a governance bug.
- **Q3 leases mint no cooldown tombstones (ruled, §6.8).** Do not "harden" the Q3-lease reap into `finalize_claim` later: Q3's atomic/CAS writes complete before lease release, so immediate F12+1 reconciliation is the expected next step; a cooldown would obstruct the normal workflow. Similarly, Q3 never consults CARTO tombstones.
- **Governing dead code.** `_maybe_create_ast_beacon_from_tags` has no call sites in the current source; remove it during cleanup rather than adding leases to it.
- Long-defer probe-claim churn (zero network traffic, self-correcting once the defer passes) and DedupeHit-onto-a-cancelling-job (ordinary active-job semantics; observe terminal, retry through cooldown) are ACCEPTED behaviors — recorded here so future audits do not re-raise them.
- **A general content-addressed / hash-passing architecture (v12, rejected).** `preparation_input_digest` (§6.6) is ONE dedupe-identity ingredient. Do not "unify" the system's deliberately distinct equivalence relations — exact-byte CAS (Q3), parsed semantic node equality (`node_data_equal`), whitened-text comparison, region footprints, launch intent — into a shared content-hash scheme: they share only §3's canonical hash ENCODING, never one meaning. A future digest is added only for an operation that participates in active-job dedupe AND carries mutation-defining preparation input not already in the key.
- **Universal runtime disk-write capability plumbing (v12, rejected for v1).** A caller allow-list on `_write_markdown_lines_sanitized` (~two dozen legitimate helper callers) would NOT prove governance — an unclaimed ingress could call an allow-listed helper — and a real seal would mean threading claim/lease ownership tokens into the disk writer: a separate future project with no current evidence of need (every known mutation ingress is inventoried and fenced at the reconcile/Q3/HTTP boundaries). ### 16.2 Cancellation flow

```
 cancel request (system.job.cancel | WS carto_cancel_job)
   1. create .cancel_requests/<job>.cancel          ← AUTHORITY (disk)   [FIRST,
      even for in-memory claimed jobs like BULK_APPLY — before any task.cancel]
   2. status := "cancelling"                        ← PRESENTATION
      (scanner overlay guarantees this presentation even if a progress
       write wins the read-modify-write race; status is NEVER stop truth)
                          │
   worker observes sentinel (≤1.25 s) → stops mutation work
     → re-reads sentinel → status := "cancelled" (persisted) → finalize_claim
   (terminal status BEFORE claim release — releasing first would drop the
    scanner's cancelling overlay and briefly re-present the job as "running")
                          │
   controller polls ≤5 s: claim released? PID dead?
      ├─ yes → outcome = cooperative
      └─ no  → exact identity: start-ticks/boot-id (U01) + "--carto-job-file <file>"
                ├─ detached + verified → terminate() → 2 s → kill()  = forced
                │   (a forced kill mid-HTTP is the accepted common case — safe,
                │    idempotent finalize; not a defect)
                ├─ in-process job (incl. F12+4 preparing/spawning)
                │                  → kill_refused_in_process_job
                └─ identity unclear → kill_refused_unverified_pid
   Status is NEVER stop authority. Claim release / PID death only.
```

```
                a farther slot refuses BEFORE ticket/state advance. The full

 INGRESS RULE:  every independently requested mutation-capable FILE/FOLDER
```

## 17. Rulings record (final — do not relitigate)

**Carried from v3/v4 (1–47, condensed; see v4 §17 for the full text):** locks/tombstones separate artifacts; admission mutex is the keystone; co-claims beat handoff; governor at the client write layer (six sites, reads ungoverned); governor fails closed (no per-process fallback); breaker closed/open/half_open with probe lease + pre-send recheck; 429 defers globally + Phase-0 `retry_after` fix; account scoping via `sha256(base_url+key)`, raw key never persisted, `parent_job_id` never on tool schemas; warning text permits governed non-overlapping parallelism; heartbeat write-once + mtime + diagnostic-only; tombstones full footprint + max-merge; full-sha256 lock filenames; explicit release ordering; Phase 0 first; no durable queue; real-subprocess tests scoped to cross-process semantics; two modules/two mutexes; MARKDOWN_GENERATE whole-life claims; bulk F12+4 real-path claims; footprint fail-closed; dedupe ≠ cooldown; psutil hard dependency; corrupt self-heals / broken fails closed; AST enforcement test; universal cooldown, `parent_job_id` continuations bypass tombstone only; no `taskkill /T` + exact-PID verification; `parent_job_id` validated; invariant card is normative.

**New in v5 (48–60):**

48. **Mutex holds are milliseconds-scale, always.** No disk mutation, governed API wait, snapshot rewrite, subprocess spawn-wait, or arbitrary callback executes while `admission.mutex` or `write_slot.mutex` is held. Prepared-launch callbacks run *under a claim, outside the mutex* — never inside the admission critical section.
49. **Launcher→worker handoff protocol for prepared launches.** Tracker states `preparing`/`spawning` (both active, deny-by-default); `execution_owner` field; launcher records child PID + create time after `Popen`, and the worker **independently self-registers** its own PID on start (closes the launcher-death race). `spawn_grace` covers the handoff; failure to appear → reap via `finalize_claim`. Originally introduced for F12+4 and generalized by v10 to F12+5/F12-on-AST.
50. **Every reap routes through `finalize_claim`.** The admission sweep, watcher loop, and startup sweep never bare-delete a claim — a reaped dead-owner claim is a terminal exit and writes its tombstone through the one exit door.
51. **Parent writes its own tombstone on failed child launch.** The §6.4 no-tombstone rule applies only to a *validated, live, successfully-launched* continuation; a refused/failed phase-8 launch means the parent's own finalize writes the tombstone.
52. **`Retry-After`: strict parse, honor valid exactly (NO downward clamp), loud conservative fallback on malformed.** Both RFC forms parsed (delta-seconds + HTTP-date; the current `int()` parser raises an unhandled `ValueError` on the date form — fixed in Phase 0). Malformed/negative/non-finite → loud log + `retry_after_fallback_seconds`. The manual override is deleting the governor/breaker state file (safe by self-heal).
53. **Exhaustive half-open probe outcome table.** 2xx→close; 429→close+defer; non-WFB 4xx→close (endpoint answered); WFB(3)→reopen+doubled; 5xx→reopen (bounded); timeout/network→reopen (bounded); probe death→lease expiry. All non-trip transitions verify `probe_claim_id`.
54. **Account-aware artifact keys.** `artifact_key = sha256(canonical_json([account_scope_id, region_key]))`; claims `<artifact_key>.<job_id>.lock.json`, tombstones `<artifact_key>.json`. Cross-account path cooldown preserved via the overlap *predicate scan*, not the key.
55. **Sentinel-sealed status presentation.** The `cancelling` overlay lives in `_scan_carto_job_files` (the guarantee: sentinel + live claim + non-terminal persisted status ⇒ presented as cancelling); the pre/post sentinel check + corrective write in the merge path is hardening, not the guarantee. Status is presentation-only.
56. **Cancel dispatch order: sentinel-first for claimed jobs.** For any job owning a claim (incl. in-memory `CARTO_BULK_APPLY`), create the sentinel (authority) and write `cancelling` (presentation) *before* any task-cancellation mechanism. Closes the sentinel-free `_jobs`-registry side door.
57. **RETIRED (U01): the epsilon create-time comparison.** Kill/liveness decisions now compare the exact clock-independent `pid_start_ticks`/`pid_boot_id` pair (integers/strings, no epsilon); `pid_create_time` is write-only provenance, never consulted. `--carto-job-file` cmdline match is exact-string.
58. **Orphaned sentinel/heartbeat reap.** A sentinel/heartbeat with no job JSON and no live claim may be deleted past `orphan_grace_seconds`; prevents unbounded accumulation under deny-by-default.
59. **Busy-timeout is a distinct loud refusal, never reported as broken.** Both remain fail-closed; the vocabulary is separate so a pathological mutex holder degrades to a named busy-timeout, not a "broken path" error.
60. **The two read sites keep their pacing sleeps.** `get_node`/`list_nodes` per-iteration `API_RATE_LIMIT_DELAY` lines are kept (reads ungoverned by the governor/breaker ≠ read pacing repealed); only the six write sites lose theirs to the governor.

**New in v6 (61–77):**

61. **The claim file is the single liveness/kill-verification authority** for owner identity (pid + the `pid_start_ticks`/`pid_boot_id` stable pair, U01; `pid_create_time` is provenance only); the job JSON's pid is a presentation mirror only. The claim carries `handoff_state` + `spawn_started_at` (mirrored to the job JSON) so the sweep never consults presentation state for authority decisions.
62. **Mutexed, verified worker claim adoption.** The worker's first action is a claim adoption under `admission.mutex`: claim absent/mismatched → exit with zero mutations; `preparing`/`spawning` → adopt; same-PID → idempotent continue; other identity → loud exit. The launcher's post-`Popen` PID record is conditional (never overwrites an adoption). Adoption applies to EVERY detached spawn, not only prepared launches.
63. **`start_grace` is presentation-only.** Age never authorizes a reap; owner-PID liveness on the claim is the only death authority. A missing/pidless/corrupt job JSON with a live owner PID is preserved untouched.
64. **Reaps preserve an already-terminal persisted status.** A dead-owner claim whose job JSON shows completed / completed_with_warnings / failed / cancelled is tombstoned and released with NO status write.
65. **Unclassifiable governance artifacts fail closed.** Malformed claims/tombstones block admission (`governance_state_unclassifiable`), are never auto-quarantined or deleted, and are preserved by every sweep/GC/clear path; governor/breaker JSON self-heal is the explicit exception.
66. **Continuation validation is the exact edge, not overlap:** active parent + `CARTO_MARKDOWN_GENERATE → CARTO_REFRESH` + same account + same canonical path (or same graph root) + exact `parent_job_id`.
67. **Claim + initial job JSON are created as one admission-mutex transaction.**
68. **The mutex rule permits the small metadata writes constituting the transaction** (claims, job identity fields, tombstones, governor/breaker JSON, adoption writes); the prohibition covers source/Workflowy mutation, API waits, snapshot rewrites, spawn waits, and callbacks.
69. **The legacy `failed → cancelled` merge transition is retired** (cancel against a terminal job answers `already_terminal`, no write).
70. **WFB while open/half-open:** never shortens `blocked_until`, never compounds doubling; a matching half-open probe WFB doubles (capped); a stale non-matching WFB trips to open at the un-doubled cooldown for that generation.
71. **The pre-send breaker recheck passes the probe holder's own reservation** (`half_open ∧ probe_claim_id == mine`).
72. **The governor sleep consults both probes:** the injected client-level callback AND the ambient job-scoped contextvar; either cancels the wait.
73. **`source_regime` is enumerated** (`standard` / `persistent_new` / `temp_override`); all governance hashes use canonical JSON-array encoding; `account_scope_id` normalizes the base URL (case, trailing slash, default port).
74. **Config defaults fixed:** `probe_lease_seconds` 120, `spawn_grace_seconds` 60, `orphan_grace_seconds` 120 (4 × start_grace).
75. **`finalize_claim` failure semantics:** tombstone-write failure blocks claim deletion (fail-closed); claim-absent/claim_id-mismatch is an idempotent no-op with a loud diagnostic; a vanished sentinel at cancel finalization yields `failed` with a loud message.
76. **CARTO_BULK_APPLY dedupe-sameness accepted** — a same-root second launch is a DedupeHit onto the active job; retry after terminal.
77. **Ancestor-chain staleness is an accepted bounded race** (captured at claim time; post-claim moves can fail the graph check open; the path check still guards disk).

**New in v7 (78–90):**

78. **Claimless non-terminal job JSONs get a degraded fallback liveness check** (F1). The claim is the single authority WHEN ONE EXISTS; a claimless non-terminal job JSON is liveness-checked against its own `pid` (no `pid_create_time` on legacy JSONs ⇒ PID-nonexistence is the only death evidence); dead/pidless-past-start_grace ⇒ persist `failed` (or `cancelled` with sentinel), NO tombstone; unknown ⇒ alive. The first post-rollout startup sweep is the migration point that terminal-izes all pre-governance crash residue — retiring the pre-existing permanent quiescence-wedge class (no PID liveness existed for detached `CARTO_REFRESH` at all).
79. **The `AdaptiveRateLimiter` retry-after axis is severed at Phase 0** (F2). The attribute fix would otherwise activate a silent process-wide stall (`acquire()` sleeps the full server-specified `Retry-After` while holding `self.lock`); the write governor is the sole 429-defer authority. The token-bucket pacing stays inert; no new role.
80. **Q3 disk mutations take symmetric transient region leases** (F3). `beacon.tags.ensure` / `tags.remove` / `sync_node` acquire all-or-nothing leases under `admission.mutex` before the first disk write; CARTO admission scans `.q3_leases/`; both launch orders refuse with `overlap_conflict`; leases release in `finally`.
81. **Q3 leases never mint tombstones and never consult them.** Cooldown exists to defer CARTO relaunches after CARTO mutation bursts; Q3→F12+1 is the expected immediate sequence. Lease reaping is plain deletion under the mutex, never `finalize_claim`.
82. **Reap write ordering and failure semantics** (R2): terminal status write FIRST (via `merge_write_carto_job_status`, which may return False), then `finalize_claim` — and a failed status write NEVER aborts the reap (loud diagnostic; the §7.1 fallback terminal-izes the residue). Region safety never hostages on a presentation write.
83. **Claim/lease/tombstone/sentinel writes are always atomic temp+`os.replace`** (R3), so lock-free readers (the 1 Hz scanner) never observe torn JSON.
84. **The blocked pre-send breaker recheck raises `AccountWriteBlockedError`** (R1) with `retry_after` = `blocked_until - now` (open) or `probe_lease_expires_at - now` (half_open).
85. **One shared sweep function, three call sites** (admission, watcher, startup) — mandated structure, not just semantic parity.
86. **Parent cancellation does not propagate to a launched phase-8 child** (F4); sentinels are job-scoped; the child finishes/fails/cancels independently.
87. **Probe-holder cooperative cancellation abandons the probe; lease expiry releases it** (F5); no proactive release-on-cancel (would reopen the one-probe invariant).
88. **Rolling-deploy mixed-version fleets are accepted** (F6): no version handshake; the all-hosts-shutdown deploy discipline is the mitigation.
89. **Implementability pins** (R4–R10): `"preparing"` in the worker adoption set is belt-and-suspenders (spawning is always set first); `dedupe_key.mode` is per-type (file/folder for REFRESH, walk mode for BULK_APPLY, `""` for MARKDOWN_GENERATE) and the Ruling-76 acceptance stands even though visible-mode trees are DOM-derived; Phase 0 hardcodes the 60 s malformed-Retry-After fallback until Phase B wires the config key; worker claim discovery is a `.<job_id>.lock.json` suffix scan + `claim_id` verification (never `artifact_key` recomputation); `.q3_leases/` is never swept by the `.refresh_claims` age-GC patterns; the presented-status vocabulary is closed (no `orphaned` string); the bulk-apply preflight ordering is a verify-don't-trust item at implementation time.

Do not newly wire RetryHandler as a second write retry/defer authority; any future use inherits the same 30 s local ceiling.

**New in v9 (103–112):**

## 18. Closed launch-origin × freshness/admission matrix (normative)

**Purpose.** This is the closed, source-derived answer to "who can start mutation-capable Cartographer work, who owns freshness, and which snapshot is consumed?" It was built from an AST scan of every live caller of `_start_carto_refresh_job`, `_start_carto_markdown_generate_job`, `_start_carto_bulk_visible_apply_job`, `_launch_post_refresh_subprocess`, the Q3 orchestrators, and the mutation-capable reconcile primitives across `src/` plus the five repo-root runtime modules. It is normative implementation input, not an audit note.

### 18.1 Freshness vocabulary and universal ordering

- **PRE** — one forced `/nodes-export` request + await BEFORE full admission. The freshness-only skip toggle may bypass the read; a usable existing snapshot is still required.
- **B0** — claim + initial job JSON are admitted first; the immediate ack is scheduled; the background task's first action under the claim is forced freshness, then preparation, spawn, finalize. Skip may bypass the read, never governance.
- **GESTURE** — one forced request + await shared by every child of one bulk gesture; never N per-child reads.
- **INHERIT** — no new request; nested/continuation work consumes the owning parent's exact snapshot and claim context.
- **NONE** — no `/nodes-export` freshness is semantically required (e.g. exact-byte Q3 CAS after its own preflight/live read).

For every **PRE** row the order is: normalize/resolve enough immutable launch input to compute `dedupe_key` → negative-only exact-intent gate (R160) → forced freshness unless skipped → recompute/resolve the footprint from the selected snapshot → full §6.3 admission → spawn/schedule → ack. The preliminary gate never admits. For every **B0** row: freeze compatibility payload + digest → compute the pre-B0 footprint from the exact payload-overlay/current-cache operands allowed by §8 → full admission → schedule task + ack → verify/obtain usable snapshot → preparation. No mutation occurs merely because freshness was skipped; absent snapshot is failure.

A governed detached worker NEVER calls `/nodes-export` itself. Its first action remains claim adoption before client/bootstrap (§8 C.4), then it loads the snapshot selected by its launch row. `freshness_disposition` is diagnostic/presentation metadata, not mutation authority.
